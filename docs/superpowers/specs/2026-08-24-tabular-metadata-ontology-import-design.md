# 表格元数据到本体包的导入设计

## 背景

Python 本体内核已经能够加载、校验和发布本体包，并根据概念、属性、规则及物理映射生成查询计划和影子 SQL。目前缺少的是可复用的业务元数据入口：用户提供的表格元数据只能由人工改写为 TTL，旧版字段导入接口又直接依赖 MySQL 元数据库，无法满足多数据平台和本体包隔离要求。

本阶段实现一个与数据库无关的 Python 导入器，将用户提供的单表 TSV 元数据生成可校验、可发布的本体包。真实业务元数据、人工修正和诊断报告仅保存在 Git 忽略的本地目录，不进入代码库。

## 目标

- 解析“对象信息”类 TSV 元数据，保留对象名称、属性名称、类型、描述和标记。
- 将一张物理表转换为一个本体概念、若干属性、一个数据源、一个对象映射和对应字段映射。
- 支持本地修正覆盖，且不修改原始附件、不在通用代码中硬编码业务内容。
- 生成结构化诊断，区分阻断错误、可发布警告和待人工确认项。
- 原子生成并校验本体包，失败时不替换当前可用包。
- 证明查询计划器能够组合未预先保存为 SQL 模板的新字段查询。
- 为后续 Excel、数据库元数据、口径文档和历史 SQL 适配器保留稳定接口。

## 非目标

- 本阶段不从字段名或描述自动生成正式业务口径。
- 本阶段不实现多表关系发现、聚合、分组或复杂时间语义。
- 本阶段不执行本体 SQL，仍保持影子预览模式。
- 本阶段不把真实表结构、修正内容或生成后的业务本体包提交到 Git。
- 本阶段不改造旧版 MySQL 元数据接口。

## 方案选择

### 方案一：手工生成 TTL

实现最快，但每张新表都要重复人工转换，无法沉淀为项目能力。

### 方案二：通用 TSV 导入器（采用）

Python 导入器解析稳定的输入 DTO，再通过生成器输出本体包。实现成本适中，可测试、可扩展，且不依赖单一数据库。

### 方案三：先写旧版 MySQL 元数据再转换

可以复用旧接口，但引入数据库连接、状态和方言耦合，与平台无关目标冲突。

## 架构

数据流如下：

```text
TSV 附件
  -> TabularMetadataParser
  -> MetadataNormalizer
  -> MetadataQualityAnalyzer
  -> LocalOverrideApplier
  -> OntologyPackageGenerator
  -> OntologyRepository 校验/发布
  -> OntologyPlanner
  -> SqlCompiler
```

### `TabularMetadataParser`

- 输入为 UTF-8 TSV 文本或文件路径。
- 按中文列名而不是固定列序读取，允许额外列存在。
- 输出数据库无关 DTO，并保留输入行号以支持精确诊断。
- 必需列为对象英文名、属性英文名；其他已知列按可选信息处理。

### `MetadataNormalizer`

- 去除单元格首尾空白并统一空值表示。
- 保留原始英文标识符大小写，另生成用于查重和匹配的标准化键。
- 将中文状态、布尔标记和字段类型映射为内部枚举；不能可靠映射时保留原值并告警。
- 单次导入只允许一个物理对象，避免不明确的跨表关系被隐式建立。

### `MetadataQualityAnalyzer`

诊断分为三级：

- `error`：缺少表名或字段名、非法物理标识符、重复字段、同一文件包含多个对象等。存在错误时禁止发布。
- `warning`：对象描述为空、属性描述为空、字段类型未知等。警告不阻止发布。
- `confirmation_required`：中文名、英文名和描述疑似冲突等，需要业务人员确认，但在没有正式业务规则的前提下可以生成本体草稿。

诊断必须包含稳定代码、严重度、输入行号、字段位置和安全消息，不在异常堆栈中泄漏完整原始行。

### `LocalOverrideApplier`

- 接收本地 JSON 或 YAML 覆盖文件。
- 使用物理字段名定位修正项，可修正中文名、描述、类型和别名。
- 不允许覆盖物理表名或字段名，避免修正配置悄然改变 SQL 目标。
- 无法匹配的修正项作为错误处理，防止拼写错误被忽略。
- 覆盖文件与生成结果存放在 `.local/` 下，由 Git 忽略。

### `OntologyPackageGenerator`

- 生成一个领域概念，并为每个字段生成一个属性。
- 中文名作为本地化标签，英文名作为稳定短名；描述作为说明信息，不直接等同于可信同义词。
- 生成数据源、表级物理映射和字段级物理映射。
- 数据库或 Schema 写入 `physicalNamespace`，表名写入 `objectName`，字段名写入 `fieldName`。
- 不生成推测性业务规则；当前生成包的业务规则数量应为零。
- 使用临时目录写入完整包，调用现有校验器通过后再原子替换目标目录。

## 业务口径生命周期

历史 SQL、测试集、字段描述和口径文档可以在后续阶段生成候选规则，但不能直接成为正式规则：

- `candidate`：系统推断或自动抽取，保存来源和置信度，不参与可执行查询计划。
- `confirmed`：业务人员确认，可以转换为查询计划约束。
- `rejected`：已确认不适用，保留审计信息，避免重复推荐。

本阶段只预留状态模型与扩展点，不从单表元数据产生候选规则。查询计划器继续只使用已确认或现有 `active` 规则。

## 查询泛化边界

历史需求不是 SQL 模板库，而是规则发现和回归测试来源。导入后，查询计划器应能对已存在于本体中的概念和属性进行新组合，例如从同一概念选择任意两个或三个已映射字段，而无需历史中出现完全相同的请求。

若需求涉及尚未定义的指标、枚举值、关联关系、聚合语义或业务规则，系统应返回缺失或歧义诊断，不能猜测 SQL。后续版本通过语义解析、关系规划和聚合计划扩展这一边界。

## 安全与隐私

- 附件只作为本地输入读取，不复制到受 Git 跟踪目录。
- 生成的业务本体包、覆盖配置和质量报告均位于 `.local/ontology-packages/` 或 `.local/ontology-imports/`。
- 通用测试使用合成元数据，不引用真实表名、字段名或描述。
- 数据源本体只保存平台类型、方言和逻辑命名空间，不保存主机、端口、用户名、密码、令牌或连接字符串。
- 任何失败消息只暴露必要的行号、列名和诊断代码。

## 错误处理

- 解析和规范化错误聚合返回，避免用户逐条修复后反复重试。
- 生成前存在 `error` 时不创建或修改目标包。
- 生成后 SHACL 或语义解析失败时保留旧包，删除临时产物。
- 覆盖配置非法或引用未知字段时终止导入。
- 服务加载新包失败时继续使用原有 SQL 链路，并将本体影子状态标记为不可用。

## 测试策略

采用测试驱动实现：

- 解析器单元测试：列名匹配、额外列、空值、行号、编码和格式错误。
- 质量测试：重复字段、非法标识符、空描述、未知类型和疑似冲突。
- 覆盖测试：合法修正、未知字段、禁止修改物理标识符。
- 生成测试：概念、属性、数据源和物理映射数量准确，且不生成业务规则。
- 原子性测试：生成或校验失败时旧包保持不变。
- 集成测试：发布合成本体包，通过 resolver、planner 和 compiler 生成字段组合 SQL。
- 回归测试：原有本体内核、影子服务和聊天接口测试继续通过。

## 本次本地验收

真实业务验收数据不写入本文档或测试代码。本地执行时应验证：

- 输入对象数、字段数与附件一致。
- 表级和字段级映射完整指向用户确认的物理命名空间。
- 用户确认的字段描述修正只存在于本地覆盖和生成包中。
- 业务规则数量为零。
- 空描述和疑似冲突形成诊断报告。
- 至少三条此前没有保存为 SQL 模板的字段组合需求能够命中并生成影子 SQL。
- 未知字段和歧义请求失败关闭，不产生猜测 SQL。
- 前后端服务启动后，聊天页可显示新本体包的证据与 SQL 对比。

## 交付边界

Git 提交只包含通用导入器、合成测试、本文档以及不涉及真实元数据的实践记录。真实导入包在本地服务中生效，待用户提供更多表、关联、口径和测试集后按同一接口增量扩展。
