# DeepSeek 结构化计划 JSON 输出设计

## 背景

当前发布本体包能够在服务启动时恢复到智能体运行时。真实聊天接口的第一条测试需求已进入本体程序规划，但 DeepSeek 返回内容未通过 `DraftSqlProgramPlan` 和 `InferredProgramDraft` 的 Pydantic 校验，导致 SQL 未生成。

根因是结构化规划请求仅在提示词中要求 JSON，没有向 DeepSeek Chat Completions API 传递 `response_format={"type":"json_object"}`。该接口的默认输出格式是文本，不能保证可解析的 JSON。

## 目标

让本体程序规划和元数据候选推断稳定返回可解析 JSON，同时保持以下行为不变：

- 自然语言问答和普通 SQL 生成仍使用文本输出。
- Pydantic、候选目录、绑定与编译校验仍是业务正确性的最终边界。
- 不记录模型原始思考内容、完整原始响应或凭据。
- 失败时仍向用户返回已脱敏、可行动的诊断。

## 方案

在 `LLMClient` 的内部请求方法增加一个仅内部使用的 `json_output` 开关。

当开关为真时，请求体增加：

```json
{"response_format":{"type":"json_object"}}
```

调用规则：

| 调用场景 | JSON 输出 | 原因 |
| --- | --- | --- |
| 本体程序初始规划 | 是 | 返回 `DraftSqlProgramPlan`，必须由程序解析。 |
| 本体程序修复规划 | 是 | 返回同一计划草案，必须由程序解析。 |
| 元数据候选推断的最终计划 | 是 | 返回 `InferredProgramDraft`，必须由程序解析。 |
| 元数据字段检索的首轮与最终轮 | 是 | 首轮既可能请求字段工具，也可能直接返回最终计划，两种结果都必须可解析。 |
| 普通 SQL、自然问答、上下文压缩 | 否 | 这些输出面向用户或是自由文本，不应强加 JSON。 |

元数据字段检索维持至多一轮的约束：首轮允许工具调用，同时启用 JSON 输出；若有第二轮，第二轮同样启用 JSON 输出。没有工具调用时，首轮直接按 JSON 输出解析。

## 错误处理与可观测性

结构化响应继续先去除完整的 Markdown JSON 围栏，再进行 Pydantic 校验。请求失败、空响应、长度截断或校验失败统一转换为现有的 `StructuredPlanningError`，不向对话或审计日志写入原始模型文本。

新增的内部诊断只记录安全元信息：响应结束原因、是否含正文和正文长度。它们只用于开发日志与自动化测试，不暴露 API 密钥、请求正文、原始模型响应或思考内容。

## 测试

采用测试先行：

1. 为程序规划添加失败测试，断言请求体带有 JSON 输出配置。
2. 为元数据推断添加失败测试，断言无工具调用的最终响应带有 JSON 输出配置。
3. 为字段检索的两轮流程添加失败测试，断言第一轮保留工具调用能力、第二轮启用 JSON 输出。
4. 运行相关单测和完整后端测试集。
5. 重启服务后，用真实聊天接口重测第 1 条需求；仅在成功获得结构化计划或明确的本体诊断后，再继续第 2 至第 7 条。

## 非目标

- 不改变本体包发布、启动恢复或版本回滚机制。
- 不取消 Pydantic 与确定性编译校验。
- 不展示或持久化模型逐字内部推理。
- 不自动执行生成的 SQL。
