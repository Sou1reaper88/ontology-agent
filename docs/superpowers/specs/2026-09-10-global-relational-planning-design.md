# 全局关系规划与 LangGraph 智能体设计

## 目标

将当前以单表和扁平关联为主的生成链路升级为通用的本体驱动关系规划内核，并使用 LangGraph 统一对话意图、工具选择、生成状态和错误分支。系统应能处理单表、多表、来源并集、维表补充、排除集合和多步骤建表，同时保持“不执行 SQL、只使用已发布本体、确定性安全编译”的边界。

本设计不为任何业务需求、物理表或字段增加专用规则。体育卡需求仅作为暴露架构问题的复现场景，不作为实现条件。

## 已确认问题

当前系统存在两套能力不一致的规划路径：

- 元数据候选规划可以选择多张表，但产物是单个扁平关联图，不能表达“多个来源先合并，再关联维表”等集合运算。
- 旧结构化程序规划的单步骤查询计划最多包含两个对象和一个内连接，无法承接复杂元数据计划失败后的回退。
- 大模型同时决定业务语义、连接方向和拓扑；确定性校验器只在末端拒绝非法图，没有通用的图解析和规范化阶段。
- `LEFT JOIN` 和 `ANTI JOIN` 的右侧必须是独立叶节点，这是必要的语义安全约束，不应放宽；上游应生成合法拓扑。
- 已发布本体的确认关系可能不完整。现有字段同名、标签和描述推断可以提供候选边，但没有统一表达边的来源、置信度和选择理由。
- 元数据计划校验失败后转入另一套能力更弱的规划器，诊断被拼接，但失败草稿、冲突节点和可修复动作没有保留。

## 总体架构

采用 LangGraph 作为顶层智能体状态机，采用一个平台无关的规范逻辑计划作为模型与编译器之间的唯一契约：

`加载上下文 → 意图识别 → 工具路由 → 元数据检索 → 动态关系证据图 → 语义逻辑计划 → 图解析与规范化 → 安全校验 → 方言编译 → SQL 程序或自然语言回答`

大模型负责理解自然语言、选择业务对象、声明期望的业务运算和解释依据。Python 内核负责绑定真实元数据、选择可验证的关系边、构建合法拓扑、解析时间、检查安全性并编译。模型不得直接决定物理 SQL。

LangGraph 只负责“智能体下一步做什么”，不承载关系验证和 SQL 编译规则。关系图、计划校验、时间推导和编译继续使用普通 Python 与 Pydantic。项目不引入 LangChain、NetworkX 或新的状态存储；会话历史继续使用现有数据库，LangGraph 状态仅服务于当前请求。

## 顶层智能体状态

每轮请求在一个统一状态中维护：

- 会话编号、消息编号、用户输入和上下文快照。
- 意图、当前工具和当前处理状态。
- 活动本体版本及摘要。
- 候选对象、字段和动态关系证据。
- 语义计划、规范逻辑计划和编译结果。
- 诊断、缺失信息、公开处理步骤和最终回答。

状态按 `received → context_ready → intent_classified → tool_running → planning → validating → compiled / clarification_required / failed → answered` 流转。逐字内部推理不进入状态、数据库或前端。

## 顶层工具

对话模型只开放三个只读工具：

- `search_ontology`：查询当前已发布本体中的对象、字段、关系、描述和版本证据，直接复用现有元数据搜索能力。
- `generate_sql_program`：接收结合会话整理后的完整需求，内部完成动态关系推断、规范计划校验和 SQL 编译；每轮最多调用一次。
- `analyze_generation`：读取指定会话、消息或最近一次生成的已有诊断与计划证据，由大模型给出需求描述或本体改进建议，不另建分析引擎。

普通概念解释直接回答。元数据搜索最多进行三轮有限工具交互；生成失败后不在同一轮自动重试，用户补充信息后可以在下一轮重新生成。本体编辑、发布、删除和 SQL 执行不开放为对话工具。

## 规范逻辑计划

统一计划采用有向无环图，每个节点有稳定 ID、输入节点和输出字段。首期节点类型如下：

- `scan`：读取一个已发布本体对象或已确认表族。
- `union_all`：合并结构兼容的多个来源，保留重复记录；不隐式使用 `UNION`。
- `join`：支持 `inner`、`left` 和 `anti`，关联条件只引用已绑定字段。
- `filter`：区分普通结果过滤和右侧匹配过滤，防止把左连接错误改成内连接。
- `project`：选择和重命名最终字段。
- `aggregate`：已有计数、求和、平均、最值、分组能力迁入统一模型。
- `materialize`：把中间节点或结果节点编译为建表步骤。

节点模型只保存语义引用、运算意图和证据，不保存任意 SQL 片段。目标表名继续由 Python 确定性生成。

## 动态关系证据图

关系图是供大模型使用和补充的证据空间，不是生成 SQL 前必须完整具备的规则库。初始关系图可以不完整，甚至没有已确认关系；大模型可以结合检索到的元数据和用户需求提出候选边。关系图的节点是逻辑数据来源，边按以下优先级产生：

1. 已发布且启用的本体关系与关联键，置信度最高。
2. 用户在当前需求或会话中明确给出的关系和字段。
3. 字段物理名、中文名、类型和描述一致产生的推断边。
4. 大模型从表描述和字段描述提出的候选边。

每条边必须记录来源、字段、类型兼容结果、方向性和置信度。低置信边可以用于候选计划，但必须在结果中展示依据；字段类型不兼容、无法绑定到同一快照或缺少关联字段时禁止编译。本体未预先配置关系本身不能成为拒绝生成的理由。

关系使用分为三级：已发布本体关系作为已确认关系；用户本轮明确说明的关系作为当前请求确认关系；大模型根据字段名、标签、类型、描述和业务主体提出的关系作为推断关系。推断关系通过真实性和结构安全检查后可以生成候选 SQL，但不得自动写回本体。

对于内连接，图解析器可以交换左右方向以连接已访问节点。对于左连接和排除连接，不允许自动反转语义；其保留侧和匹配侧必须由业务计划明确。

## 来源合并

多张表代表同类业务事件时，使用 `union_all` 节点后再参与关联，避免用多个连接错误表达来源并集。

来源合并依据依次为：已发布表族或来源组、用户明确说明、表描述中的同类来源信息、模型提出且通过结构兼容校验的候选。结构兼容至少检查输出字段映射、数据类型和必要时间字段。没有足够依据时返回可理解的待确认项，不静默合并。

现有基于物理命名识别的表族作为一种来源组继续支持，但不再是唯一的并集表达方式。后续本体管理应允许显式维护来源组及成员映射。

## 图解析和规范化

图解析器以最终输出字段所属节点和业务保留集合为锚点，构造覆盖所选来源的合法连接树：

- 内连接可以无损重排方向，但不能改变连接条件。
- 左连接和排除连接的右侧保持独立分支；需要复用时先生成独立子计划，再在上层引用结果。
- 多个等价来源先形成 `union_all`，再与维表或主表关联。
- 无法连通的对象不生成笛卡尔积。
- 多条候选路径按关系优先级、置信度、路径长度和字段类型确定性排序；完全并列时交给模型或用户确认，不随机选择。

规范化仅修复不改变业务含义的结构问题，例如内连接方向、节点顺序和重复扫描。任何可能改变保留集合、排除含义或聚合粒度的调整都不能静默执行。

## 失败处理

校验失败时返回机器可读诊断，包括失败阶段、节点、涉及对象和字段、违反的规则以及建议补充的信息。错误至少区分：模型或网络服务错误、元数据未命中、关系证据不足、业务口径待确认、计划结构非法、编译器不支持和安全校验失败。

- Python 可以确定性完成内连接方向、节点顺序、重复扫描和明确来源组等不改变业务含义的规范化。
- 来源是否合并、左连接保留侧、排除集合和聚合粒度等可能改变业务含义的问题必须返回待确认信息。
- 网络、鉴权、限流、活动本体版本变化和模型输出不符合契约时不自动重试。

诊断和最终计划摘要进入处理过程，但不展示模型逐字内部推理。

## 统一规划链路与直接切换

实施分为以下可独立提交的阶段：

1. 已完成规范逻辑计划、集合节点和通用编译器。
2. 增加动态关系证据图与拓扑规范化，将当前元数据规划产物转换为规范计划。
3. 让规范计划直接接管 `generate_sql_program`，停止旧结构化规划器和旧 LangGraph SQL 图的自动回退。
4. 使用新的 LangGraph 顶层状态机替换手写对话工具循环，并接入三个只读工具。
5. 使用七条真实需求走正式会话链路验证，再升级评测中心、补充来源组管理并删除旧实现。

不进行影子双跑，也不同时返回两份 SQL。服务端只保留一个人工回滚配置，默认使用规范链路；人工切换到旧链路时整轮请求只走旧链路，任何失败都不得自动回退。新链路完成并通过对应测试后直接成为正式输出。

## 可观测性与前端反馈

处理过程应区分以下阶段：上下文加载、意图识别、工具选择、候选检索、元数据搜索、关系证据构建、计划规范化、安全校验和方言编译。失败时显示具体节点和可行动原因，避免统一显示“业务存在歧义”。

真实模型复测通过独立的“系统复测”会话走正式 API，以便用户看到输入、回答、SQL、处理步骤以及 `C-... / M-...` 编号。纯单元测试继续隔离运行，不写入会话数据库；两类测试须在结果说明中明确区分。

日志记录异常类型、HTTP 状态和阶段，不记录 API 密钥、完整敏感业务输入或模型内部推理原文。

## 安全边界

- 仅生成 SQL 程序，不连接业务数据库、不执行脚本。
- 物理对象和字段必须来自同一不可变已发布本体快照。
- 不允许大模型注入 SQL、目标表名或未发布物理标识符。
- 不放宽笛卡尔积、字段归属、数据类型、时间范围和标识符检查。
- 不因低置信关系静默改变连接语义。
- 本体关系不完整时允许大模型提出候选关系，但必须绑定真实字段、记录证据并通过安全校验。
- 对话智能体不得修改本体或执行生成的 SQL。
- SQL 方言通过编译器接口扩展，不在逻辑计划中写入 Hive 专用结构。

## 测试与验收

单元与属性测试覆盖：

- 单表查询保持兼容。
- 三张及以上表的连通关系图。
- 多来源 `union_all` 后关联维表。
- 内连接方向无损规范化。
- 左连接和排除连接方向不可被静默改变。
- 断图、环、重复节点、不兼容字段和跨快照引用被拒绝。
- 默认日/月账期继续由时间策略确定性解析。
- 模型或网络失败不在同一轮自动重试。
- LangGraph 意图路由、工具次数限制、成功和失败状态均可独立测试。
- `search_ontology` 和 `analyze_generation` 只读，`generate_sql_program` 每轮最多调用一次。
- Hive 编译结果可被 SQL 解析器解析，且只产生建表程序、不含末尾清理语句。

集成验收使用通用测试集而非单一需求，至少包含：单表、普通多表、维表补充、两个来源并集、排除集合、地市表族、显式账期和默认账期。C-2419 仅作为其中一个回归样例。

成功标准不是“某条 SQL 被生成”，而是相同语义在不同表名和字段名夹具下都能形成等价逻辑计划，正式会话能够选择正确工具，并且错误能稳定归入检索、关系、业务语义、校验、模型服务或编译阶段。

## 非目标

- 本阶段不执行生成 SQL，也不校验真实数据结果。
- 不一次性支持窗口函数、递归查询、任意子查询和所有 SQL 语法。
- 不用关键词硬编码特定业务口径、表名、字段名或 D/H 表关系。
- 不自动把所有同构表视为可以合并；来源语义仍需证据。
