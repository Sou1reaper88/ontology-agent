# 本体驱动时间分区策略设计

## 1. 背景与问题

当前 Python 本体内核已经能够根据本体属性和物理映射选择字段、生成 SQL，但导入的月表虽然包含 `P_MON`（时间分区），本体包并没有声明它是必须使用的分区属性，也没有描述默认账期如何计算。因此，本体查询命中后仍可能生成不带分区条件的 SQL，形成全表扫描风险。

旧编排器已有日期推算逻辑：基于系统时间计算 `p_day = T-2`，并把上一个完整自然月作为 `p_mon`。这部分逻辑目前散落在旧编排器中，未进入本体模型、查询计划及可解释证据链。

本设计把时间分区字段及默认计算策略建模为本体事实，并在自然语言到查询计划的阶段解析用户时间意图。只要一个查询对象声明了时间分区策略，编译得到的 SQL 就必须包含对应的有界分区谓词，不允许失败后退化为全表查询。

## 2. 已确认决策

1. 采用本体声明时间分区策略，不根据 `P_MON`、`P_DAY` 等字段名在 Python 中硬编码判断。
2. 不实现、也不为“查询数据库最新可用分区”预留接口。
3. 系统时间为 `2026-08-24` 时，默认推算 `p_day=20260822`、`p_mon=202607`。
4. 用户需求明确指定时间时，用户时间优先于默认推算。
5. 同一张表不会同时存在日、月两种时间分区粒度；每个查询对象至多绑定一条激活的时间分区策略。
6. 月表默认使用上一个完整自然月，日表默认使用 `T-2`。
7. 无边界历史查询、冲突时间、无效系统时间及不完整策略均失败关闭，不能生成无分区条件的 SQL。
8. 当前真实表名、字段和覆盖配置继续保存在 `.local` 目录，不提交到 Git。
9. 每个独立逻辑改动在验证后自动创建 Git 提交；未经明确授权不推送远端或合并分支。

## 3. 目标与非目标

### 3.1 目标

- 在本体中明确声明查询对象的分区属性、粒度、默认算法和覆盖规则。
- 确定性解析常见中文时间表达，并区分分区时间与其他业务日期属性。
- 将解析后的具体时间谓词及决策证据写入数据库无关的 `QueryPlan`。
- 确保任何声明时间策略的对象都不会生成无分区条件 SQL。
- 在聊天页面展示账期推算依据和最终结果，使优化可见、可验收。
- 保持 SQL 编译器只负责方言输出，不承担日期推算或自然语言理解。

### 3.2 非目标

- 不连接数据库查询最大分区或入仓状态。
- 不实现关账日历、节假日日历或外部业务日历。
- 不允许 LLM 独立决定最终分区值。
- 不在生产代码或被 Git 跟踪的示例中写入当前真实业务表元数据。
- 不把当前任务扩展为通用日期维表、指标窗口或任意时间序列计算框架。
- 不实现全量本体可视化编辑器；当前策略通过导入覆盖配置维护。

## 4. 总体架构

```text
用户需求 + system_time
          │
          ▼
确定性时间意图解析器
          │ TemporalIntent
          ▼
本体时间分区策略 + 物理映射
          │ TemporalDecision
          ▼
带已解析时间谓词的 QueryPlan
          │
          ▼
数据库方言编译器
          │
          ▼
含有界 WHERE 分区条件的 SQL
```

职责边界如下：

- 本体包回答“哪个属性是时间分区、是什么粒度、默认如何取值”。
- 时间解析器回答“用户是否指定时间、指定了什么时间”。
- 时间策略解析器回答“结合系统时间与本体策略，最终分区条件是什么”。
- 查询规划器负责把时间决策与字段选择、业务规则组装成一个查询计划。
- 编译器只把结构化谓词转换为目标方言 SQL。
- 前端展示后端返回的时间决策证据，不在浏览器中重复计算账期。

## 5. 本体模型

### 5.1 TemporalPartitionPolicy

新增独立语义对象 `TemporalPartitionPolicy`，至少包含：

- `uri`、`short_name`、`label`：稳定标识及显示信息。
- `applies_to_uri`：策略适用的概念 URI。
- `partition_property_uri`：时间分区属性 URI。
- `grain`：`day` 或 `month`。
- `default_strategy`：`t_minus_2` 或 `previous_complete_month`。
- `allow_query_override`：是否允许用户显式时间覆盖默认值；当前固定为 `true`。
- `status`、`priority`：与现有规则和映射一致的启停及冲突决策字段。

概念与策略是一对零或一关系。一个概念可以没有时间分区策略，例如无需分区过滤的小型维表；一旦声明了激活策略，该策略就成为查询安全约束。

本体 Turtle 表达示意：

```turtle
ex:MonthlySnapshotPolicy a oa:TemporalPartitionPolicy ;
    oa:shortName "MonthlySnapshotPolicy" ;
    rdfs:label "月快照默认账期"@zh-CN ;
    oa:appliesTo ex:CustomerSnapshot ;
    oa:partitionProperty ex:AccountingMonth ;
    oa:partitionGrain "month" ;
    oa:defaultStrategy "previous_complete_month" ;
    oa:allowQueryOverride true ;
    oa:status "active" ;
    oa:priority 100 .
```

示意名称只描述通用模型，不包含用户的真实表名或字段名。

### 5.2 SHACL 约束

新增约束至少验证：

- 策略必须且只能引用一个概念及一个属性。
- 分区属性必须属于策略适用概念。
- `month` 只能配合 `previous_complete_month`。
- `day` 只能配合 `t_minus_2`。
- 同一概念不能存在多个同优先级激活策略。
- 分区属性在目标数据源中必须存在可用字段映射。
- `allow_query_override` 必须为布尔值。

违反约束的本体包不能发布为激活快照。

## 6. 元数据导入与本地覆盖

表格元数据中的字段名称或“时间分区”标签只能作为候选提示，不能静默生成权威策略。导入诊断可以提示用户确认候选字段；确认后由本地覆盖文件写入：

```json
{
  "temporal_policy": {
    "field": "P_MON",
    "grain": "month",
    "default_strategy": "previous_complete_month",
    "allow_query_override": true
  }
}
```

发布器校验字段存在、粒度与策略匹配后，把它确定性转换为 `rules.ttl` 中的 `TemporalPartitionPolicy`。当前业务覆盖文件继续位于被 Git 忽略的 `.local` 路径；仓库测试使用匿名夹具。

## 7. 时间意图解析

### 7.1 输入与输出

解析器输入：

- 原始用户需求。
- 严格解析后的 `system_time`。
- 本体策略声明的分区粒度。
- 当前概念的日期类属性及别名，用于区分分区时间与业务日期。

解析器输出 `TemporalIntent`：

- `target`：分区属性或其他已识别日期属性。
- `kind`：单值、闭区间或最近 N 个周期。
- `start`、`end`：规范化后的 `YYYYMM` 或 `YYYYMMDD`。
- `source`：`explicit_absolute`、`explicit_relative` 或 `ontology_default`。
- `matched_text`：触发解析的原始文本片段。
- `explanation`：供 API 和页面展示的中文说明。

### 7.2 支持范围

月粒度首期支持：

- 单月：`2026年6月`、`202606`、`2026-06`、`6月`。
- 范围：`2026年4月至6月`。
- 相对时间：`本月`、`上月`、`最近3个月`、`最近3个账期`。

日粒度首期支持明确日期、日期范围及常见相对日表达。日表未指定时间时使用 `T-2`。

只有“账期 6 月”“6 月数据”“查询 6 月用户”等可归属于查询快照的表达覆盖默认分区。“6 月入网用户”这类与其他业务日期属性相邻的时间表达不覆盖分区；查询仍应用默认分区，并把业务日期条件交给相应属性谓词处理。若当前查询规划器无法完整表达该业务日期条件，则拒绝生成不完整 SQL，而不是丢弃条件。

### 7.3 优先级

1. 用户明确指定的绝对分区时间。
2. 用户明确指定的相对分区时间。
3. 本体声明的默认策略。

系统时间 `2026-08-24` 的典型结果：

- 未指定时间，月表：`202607`。
- “查询 6 月用户”：`202606`。
- “查询本月用户”：`202608`，即使当月尚未完整也尊重用户显式要求。
- “最近 3 个账期”：`202605` 至 `202607`。

未写年份的月份按 `system_time` 所在年份解释，并在证据中明确展示推断年份。

### 7.4 冲突与歧义

以下需求同时给同一分区属性两个无法并存的值：

```text
查询2026年5月用户，账期按202606。
```

系统识别到 `202605` 与 `202606` 冲突，返回结构化澄清问题，不生成 SQL。

明确范围不属于冲突：

```text
查询2026年5月至6月的数据。
```

不同属性上的时间也不属于冲突：

```text
查询2026年6月入网、账期为202607的用户。
```

此时入网日期和分区账期分别形成谓词。

## 8. 查询计划模型

`QueryPlan` 增加数据库无关的已解析过滤条件和时间决策：

```python
class ResolvedFilter(FrozenModel):
    property: BoundProperty
    operator: RuleOperator
    values: tuple[RdfLiteral, ...]
    source: str
    explanation: str


class TemporalDecision(FrozenModel):
    partition_property_uri: str
    grain: str
    source: str
    system_date: date
    matched_text: str | None
    resolved_start: str
    resolved_end: str
    explanation: str


class QueryPlan(FrozenModel):
    # 现有字段保持不变
    filters: tuple[ResolvedFilter, ...] = ()
    temporal_decision: TemporalDecision | None = None
```

单值编译为 `=`，连续闭区间编译为 `BETWEEN`；规范化时间值以有类型字面量进入编译器，不拼接用户原始文本。

分区属性只参与过滤。除非用户明确要求返回账期，否则不会因为分区过滤而自动加入 `SELECT`。

## 9. 数据流与错误处理

完整流程：

1. 规划器匹配概念、查询属性及物理数据源。
2. Resolver 读取该概念唯一激活的时间分区策略。
3. 严格解析 `system_time`；格式错误立即返回错误，不回退当前机器时间。
4. 时间意图解析器分析用户需求并将时间绑定到分区或其他日期属性。
5. 无显式分区时间时，根据本体策略计算默认值。
6. 验证分区属性存在目标数据源字段映射。
7. 构建 `ResolvedFilter` 和 `TemporalDecision`，加入 `QueryPlan`。
8. 查询计划安全校验器确认：声明时间策略的计划必须包含与该属性对应的有界谓词。
9. 编译器生成 SQL；页面展示 SQL 与时间决策证据。

下列情况返回结构化错误且不生成 SQL：

- 多个时间表达争夺同一分区属性且不能解释为范围。
- 用户要求“全部历史”“不限时间”等无边界扫描。
- 用户时间粒度与表分区粒度不兼容且无法无歧义规范化。
- `system_time` 无效。
- 本体策略字段缺失、枚举不合法或多个策略冲突。
- 分区属性缺少当前数据源物理映射。
- 业务日期条件已识别但查询规划器无法完整表达。

失败关闭只适用于声明时间分区策略的对象；没有策略的非分区对象保持现有查询行为。

## 10. 编译器行为

编译器不读取系统时钟、不解析自然语言，也不知道“上月”或 `T-2`。它只编译 `QueryPlan.filters` 中的结构化谓词，并与现有业务规则谓词使用 `AND` 组合。

系统时间 `2026-08-24`、用户未指定时间时，月表查询示意：

```sql
SELECT "CUSTOMER_ID", "USER_ID"
FROM "example_namespace"."monthly_snapshot"
WHERE "ACCOUNTING_MONTH" = '202607';
```

这种边界确保以后增加其他 SQL 方言时，各编译器共享同一个账期决策，不会重复实现日期口径。

## 11. API 与前端可解释性

本体运行结果增加“业务账期决策”证据，至少返回：

- 分区字段及粒度。
- 策略来源为本体声明。
- 系统时间。
- 用户是否指定时间及命中文本。
- 默认算法。
- 最终账期或范围。
- 分区安全约束是否已加入查询计划。

页面在 SQL 结果附近展示独立信息块，例如：

```text
时间分区字段：P_MON
分区粒度：月
策略来源：本体声明
系统时间：2026-08-24
用户时间：未指定
默认算法：上一个完整自然月
最终账期：202607
安全状态：已添加分区约束
```

该信息完全来自后端的 `TemporalDecision`，前端不重新计算或猜测。

### 12.2 集成测试

- 本体包加载后 Resolver 能返回唯一时间策略。
- `system_time=2026-08-24`、未指定时间时，月表 SQL 包含 `WHERE ... = '202607'`。
- “查询 2026 年 6 月数据”覆盖默认值并生成 `202606`。
- “查询 2026 年 4 月至 6 月数据”生成有界范围。

## 14. 主要风险与控制

- **自然语言时间误绑定**：使用日期属性别名和邻近语义做确定性归属；无法确定时澄清，不让 LLM 静默选择。
- **旧代码继续绕过策略**：查询计划安全校验作为编译前硬门槛，不能仅依赖提示词或页面检查。
- **真实元数据泄露**：真实覆盖和生成包保持在 `.local`；仓库只提交匿名测试夹具。
- **编译器耦合业务口径**：编译器只消费规范化谓词，所有时间决策在查询计划之前完成。
- **功能看不见**：API 返回结构化证据，页面紧邻 SQL 展示最终账期及来源。
- **显式大范围仍可能昂贵**：首期拒绝无边界历史查询；有明确边界的范围按用户需求执行，不静默截断。

## 15. 完成标准

满足以下条件后，本设计对应功能才视为完成：

- 当前本地月表的普通字段查询不再生成全表 SQL。
- 默认账期和用户指定账期均由自动化测试证明正确。
- 任一声明时间策略的查询计划都无法绕过分区谓词安全校验。
- 页面可见完整账期决策链，而非只显示最终 SQL。
- 真实业务元数据未进入 Git。
- 相关测试、完整 Python 测试及前端构建通过。
- 服务已启动并可由用户在现有聊天页面直接验收。
- 技术难点与解决方式已记录到项目实践日志。
