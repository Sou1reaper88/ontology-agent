# 本体包管理与多表评测首期设计

## 1. 背景

项目已经具备 Python 本体内核、RDF/OWL/SHACL 本体包、表格元数据导入、只读 Resolver、数据库无关 QueryPlan、Generic SQL 编译器、本体 SQL 影子模式和表级时间分区策略。当前真实本地包只有一个对象，无法形成有代表性的多表评测；现有 `/ontology` 页面主要维护旧 MySQL 元数据，并不是新 RDF 本体包的事实源。

本阶段优先建设本体管理能力，使用户可以通过页面把多张表安全加入同一个草稿包，维护字段、关系和时间策略，校验后显式发布不可变 RDF 版本，并让 Agent 原子加载或回滚已发布快照。

## 2. 已确认决策

- 首期入口为 TSV、TXT 和无宏 XLSX 上传，不接数据库。
- 多张表先进入当前“草稿本体包”，不要求导入前判断业务域；自动分域和拆包不在首期范围。
- 普通新增导入遇到任意重复表时，整个批次拒绝，不跳过、不覆盖、不部分成功。
- 导入只改变草稿；只有用户显式发布后才影响 Agent。
- 技术路线采用“结构化草稿 + 不可变 RDF 版本”。页面不直接编辑 TTL。
- 首期管理对象、字段、单跳表关系、关联键和表级完整时间策略；不建设完整业务规则编辑器。
- 每张需要分区保护的表显式声明分区字段、粒度、默认算法和是否允许查询覆盖，不依赖 Agent 全局默认。
- 为使多表元数据可立即用于评测，首期同时交付一条已确认关系驱动的双表 JOIN 最小消费闭环。

## 3. 目标与成功标准

### 3.1 目标

1. 在不写代码、不手工编辑 TTL 的情况下向一个草稿包原子导入多张表。
2. 在页面中查看和修改表/字段描述，定义表关系、关联键和时间策略。
3. 对草稿执行结构、引用、SHACL 和 Python 语义校验，并清楚区分错误、警告和待确认项。
4. 发布不可变版本，Agent 无需重启即可原子切换快照；失败时保持旧版本。
5. 查看发布历史并回滚到任一仍有效的旧版本。
6. 让 Planner 在无歧义的一条已确认关系上生成双表 JOIN，用于首批多表评测。

### 3.2 首期成功标准

- 一次上传至少三张不同表并原子写入同一草稿。
- 含重复表的批次整体失败，草稿字节内容和修订号不变。
- 页面能完成表/字段描述、关系、关联键和时间策略维护。
- 未处理错误或待确认项时不能发布；警告不阻断发布但在确认页展示。
- 发布成功后 Agent 热加载新摘要；发布失败后激活版本和快照均不变化。
- 单表请求可分别命中新增对象；一个双表请求只能使用已确认关联键。
- 回滚后 Agent 恢复目标旧版本行为。
- 上传元数据、结构化草稿和真实 RDF 版本不进入应用代码 Git。

## 4. 非目标

- 数据库直连、自动扫描或同步表结构。
- 自动判断业务域、自动拆包或跨包关系。
- 普通新增导入覆盖或合并已有表；已有表更新另设专门差异流程。
- 完整结构化业务规则编辑器和指标口径管理。
- 三表以上、多跳 JOIN、自动关系推断或模糊路径选择。
- 自动执行本体 SQL；仍保持影子模式。
- 多节点分布式草稿协作、审批流或复杂分支合并。
- 将旧 MySQL 元数据继续作为新 RDF 包的写入事实源。

## 5. 总体架构

### 5.1 组件

#### DraftStore

定义与底层存储无关的草稿读写协议。首期实现外部文件目录版本，保存结构化草稿、修订号、诊断和导入暂存信息；未来可以新增数据库实现而不改变 API、Builder 或 Runtime。

#### BatchImportService

接收多文件上传，解析为规范化对象集合，计算内容摘要并检查批次内部及当前草稿中的重复物理身份。物理身份由逻辑数据源、物理命名空间和规范化对象名共同组成，避免把不同命名空间的同名表误判为重复。预览阶段不修改草稿；确认阶段在相同输入摘要和预期修订号下原子加入全部对象。

#### DraftEditor

提供对象/字段描述、关系、关联键和时间策略的结构化增删改查。每次写入必须携带 `expected_revision`；成功后修订号递增，冲突返回稳定错误而不覆盖较新草稿。

#### DraftValidator

执行草稿级快速校验和发布前完整校验，输出稳定的 `error`、`warning`、`confirmation_required` 诊断。发布要求 error 与 confirmation_required 数量均为零。

#### PackageBuilder

复用并扩展现有元数据包生成能力，将多对象草稿确定性生成为固定六文件本体包：`manifest.yaml`、`core.ttl`、`domain.ttl`、`mappings.ttl`、`rules.ttl`、`shapes.ttl`。同一草稿、版本和配置必须生成相同语义内容。

#### PackagePublisher

在同级随机暂存目录生成候选包，执行清单、路径、Turtle、SHACL 和 Python 语义校验；全部成功后保存为新的只读版本，并协调激活指针与 Runtime 快照原子切换。失败不修改当前版本。

#### OntologyRuntime

只消费已发布版本。草稿保存、预览和校验不会改变查询行为。发布或回滚成功后，在锁内一次性替换不可变快照；请求只能看到完整旧快照或完整新快照。

#### Relation-aware Planner

在现有单对象 Planner 上增加最小单跳关系规划。只有请求属性分属两个概念、两概念之间恰有一条已启用且映射完整的直接关系时才生成 JOIN；其余情况失败关闭。

### 5.2 存储布局

管理根目录由环境配置显式指定，位于应用代码仓库之外：

```text
ontology-management-root/
  workspaces/
    evaluation/
      draft.json
      diagnostics.json
      imports/
      versions/
        1.0.0/
          manifest.yaml
          core.ttl
          domain.ttl
          mappings.ttl
          rules.ttl
          shapes.ttl
        1.1.0/
          ...
      active-version.json
```

`draft.json` 是结构化编辑事实源；`versions/<version>/` 是发布事实和运行时输入。已发布目录不可就地修改。上传原文件只存在于受控暂存期，确认或取消后删除；长期仅保存规范化元数据、原文件名和 SHA-256 摘要。

## 6. 草稿数据模型

工作区草稿至少包含：

- 工作区 ID、展示名、包 ID、base URI、当前修订号和更新时间。
- 一个逻辑数据源：平台类型、SQL 方言和物理命名空间；不包含连接凭据。
- 对象：稳定 ID、物理对象名、中文名、描述和属性集合。
- 属性：稳定 ID、物理字段名、中文名、描述、规范化 XSD 类型和键/标题标记。
- 关系：稳定 ID、源对象/属性、目标对象/属性、方向、基数、标签、状态和优先级。
- 时间策略：适用对象、分区属性、日/月粒度、默认算法、查询覆盖开关、状态和优先级。
- 诊断处置：诊断稳定 ID、状态、处置说明、处置人和处置时间。

稳定 ID 在首次导入时根据包 base URI、逻辑数据源、物理命名空间和规范化物理标识生成，展示文案变化不改变 ID。草稿序列化排序稳定，以便审计、摘要和差异比较。

## 7. 导入流程

### 7.1 支持格式

- UTF-8 TSV/TXT，沿用当前中文列名契约。
- 无宏 `.xlsx`，每个可识别工作表可以包含一个或多个对象；公式只读取缓存文本结果，不执行宏或外部链接。
- 拒绝 `.xls`、`.xlsm`、未知扩展名、超限文件、空文件和压缩炸弹风险输入。

### 7.2 预览

1. 前端上传一个或多个文件及当前修订号。
2. 服务端在受控暂存目录解析并生成候选对象、诊断、对象/字段计数和文件摘要。
3. 按“逻辑数据源 + 物理命名空间 + 规范化对象名”检查同一批次及当前草稿中的重复物理身份。
4. 任意重复、结构错误或安全错误使预览状态为 `blocked`，且不产生可确认导入令牌。
5. 可接受预览返回短期、单次使用、绑定工作区/修订号/摘要的导入令牌。

### 7.3 确认

1. 用户确认预览并提交导入令牌与当前修订号。
2. 服务端重新核验令牌、文件摘要和草稿修订号。
3. 候选对象一次性写入新草稿文件，再通过原子替换提交。
4. 任一步失败均不改变原草稿；成功后令牌失效，修订号递增一次。

普通新增导入永不跳过、覆盖或合并重复对象。

## 8. 编辑与并发控制

页面保存表描述、字段描述、关系或时间策略时必须发送 `expected_revision`。服务端在工作区锁内比较当前修订号：相同才创建完整新草稿并原子替换，不同则返回 `409 draft_revision_conflict` 和最新修订号。

对象或属性删除属于破坏性操作：首期只允许删除尚未发布且没有关系、策略或其他引用的草稿对象；要求明确确认。已发布对象的结构更新、删除和重命名不在普通编辑范围内。

## 9. 校验与诊断

### 9.1 阻断错误

- 非法或重复稳定标识。
- 缺失必填对象/属性字段或不支持的类型。
- 关系引用不存在的对象/属性，源/目标属性不属于相应对象。
- 关系缺少物理关联字段映射或两个字段类型不兼容。
- 时间策略引用非本对象属性、字段无映射、粒度与默认算法不匹配。
- 同一对象存在多个冲突的激活时间策略。
- 路径、凭据、RDF 引用、SHACL 或语义校验失败。

### 9.2 待确认

- 字段中文名与描述存在高置信度冲突。
- 关系基数、方向或标签缺少人工确认。
- 导入元数据中的关键业务描述相互矛盾。

待确认项必须被修正或记录明确处置后才允许发布。

### 9.3 警告

- 非关键描述为空。
- 对象暂未配置关系或时间策略。
- 未被当前 Planner 消费的可选元数据。

警告允许发布，但必须在发布确认页完整展示并写入审计摘要。

## 10. 发布、热更新与回滚

### 10.1 发布

用户提交明确的新版本号、发布说明和预期草稿修订号。版本号在同一工作区内唯一且不可复用。Publisher 在工作区发布锁内执行：

1. 确认修订号未变化且无阻断诊断。
2. 在同级随机暂存目录生成六文件候选包。
3. 使用现有 OntologyRepository 完成全套校验并构造候选快照。
4. 将候选目录原子提交为只读版本目录。
5. 在协调锁内先原子写入激活指针，再执行不会失败的不可变快照引用赋值；候选快照已在锁外完整构造。若进程在两次赋值之间终止，重启时以新激活指针恢复同一候选快照。
6. 写入不包含真实元数据内容的发布审计记录。

如果第 5 步不能完成，激活指针和 Runtime 保持旧值，新版本目录可保留为未激活有效版本，供后续重试，不得被误报为已发布。

### 10.2 回滚

管理员选择已有有效版本并填写原因。系统重新验证目标包，成功后使用与发布相同的协调切换机制更新激活指针和快照。回滚不修改、不复制旧版本目录，也不改变草稿内容。

服务进程启动时以 `active-version.json` 为恢复事实，校验其目标后加载；目标不存在或无效时就绪状态降级，不能静默选择其他版本。

## 11. 最小双表关系消费

管理关系不仅用于展示，发布后进入 Resolver 和 QueryPlan：

- Resolver 返回概念关系及其已确认物理关联字段。
- Planner 可从请求字段推断至多两个概念。
- 两概念之间必须恰有一条启用且优先级明确的直接关系。
- QueryPlan 显式记录左右对象绑定、JOIN 类型和两侧字段绑定。
- 编译器只编译结构化 JOIN，不接受任意 SQL 条件片段。
- 每个有时间策略的参与对象都必须满足各自有界分区安全门。
- 多个同优先级路径、字段映射缺失、关系类型不支持或超过两张表时返回安全的 unsupported/ambiguous 状态。

首期只支持等值 `INNER JOIN`。LEFT/RIGHT/FULL、非等值 JOIN 和多跳路径留待独立设计。

## 12. API 与页面

### 12.1 API 边界

新增独立的本体包管理 API，而不是复用旧 MySQL 元数据写接口。能力包括：

- 读取工作区概览、草稿对象、关系、时间策略和诊断。
- 创建导入预览、确认原子导入。
- 使用预期修订号修改草稿。
- 运行完整校验。
- 列出版本、发布版本、回滚版本。
- 读取当前激活版本公开摘要。

API 按权限返回页面所需的结构化对象、字段、关系和策略，不提供完整草稿文件或本体包下载，也不返回服务器绝对路径、原始 TTL 和上传文件内容。错误使用稳定 code、用户安全 message 和脱敏 details。

### 12.2 页面结构

`/ontology` 改为本体包工作台：

- 概览：草稿修订号、当前激活版本、元素计数和发布状态。
- 对象与字段：多对象列表、描述维护和字段搜索。
- 表关系：源/目标对象与字段选择、方向、基数和状态。
- 时间策略：按对象维护完整表级策略。
- 诊断中心：按级别、对象和处置状态筛选。
- 版本记录：发布摘要、激活标记和回滚入口。

旧 MySQL 管理接口首期保留兼容，但新页面不再以其结果构建或发布 RDF 包。旧功能应明确标记为 legacy，避免用户误认为修改已影响新本体快照。

## 13. 权限、审计与隐私

- 已认证普通用户可以读取已发布摘要。
- 本体维护者可以导入、编辑草稿和运行校验。
- 管理员可以发布、回滚和执行破坏性草稿操作。
- 所有写操作记录操作者、工作区、修订号、动作、结果、时间和安全摘要。
- 管理根路径必须经配置提供并规范化；所有目标路径必须验证仍位于根目录内。
- 拒绝符号链接/reparse point 逃逸、路径穿越和宽泛文件操作。
- DataSource 和 PhysicalMapping 不允许主机、端口、用户名、密码、Token、Secret 或连接字符串谓词。
- 真实上传、草稿和版本目录不得位于应用 Git 跟踪范围；启动时进行边界检查并失败关闭。

## 14. 测试策略

### 14.1 单元测试

- 多文件 TSV/XLSX 解析、规范化和稳定序列化。
- 批次内/草稿内重复检测及原子不变性。
- 导入令牌摘要、修订号和单次使用约束。
- DraftStore 原子提交、修订冲突和依赖删除保护。
- 关系与时间策略引用、类型和组合校验。
- 多对象 RDF 生成确定性及版本不可变性。

### 14.2 集成测试

- 预览—确认—编辑—校验—发布完整 API 流程。
- 权限和审计，错误响应不泄露路径或上传内容。
- 候选生成、SHACL/语义失败、激活切换失败时旧版本不变。
- 热更新和回滚后，新请求读取正确快照。
- 一张/两张表 QueryPlan 与 SQL 编译；关系歧义、多跳和每表时间安全门失败关闭。
- 对话 API 持久化正确的本体版本、关系和时间证据。

### 14.3 前端与人工验收

- TypeScript 和 Vite production build。
- 多文件上传预览、重复批次阻断、修订冲突刷新提示。
- 对象/字段、关系、时间策略、诊断和版本页面关键交互。
- 使用忽略目录中的至少三张真实元数据表完成端到端验收。
- 服务启动后验证健康检查、页面访问、发布热更新、双表影子 SQL 和回滚。

## 15. 风险与后续演进

- 文件型 DraftStore 适合首期单机；多节点协作前必须实现共享存储与分布式协调，不能直接共享目录冒充事务。
- Excel 元数据格式可能不一致；首期严格使用可解释列映射并输出位置诊断，不引入模型猜测。
- 双表 Planner 仅证明关系消费闭环；测试集分类后再设计多跳路径选择、JOIN 类型和代价策略。
- 已有表更新需要独立的差异、引用影响分析和确认流程，不能复用新增导入绕过安全边界。
- 业务规则编辑器应继续使用结构化表达式，不允许保存任意 SQL 片段。

## 16. 交付顺序

1. 草稿模型、文件 DraftStore、原子导入与诊断。
2. 草稿编辑、关系和表级时间策略管理。
3. 多对象 PackageBuilder、版本发布、热更新和回滚。
4. 本体管理 API 和 `/ontology` 工作台。
5. Resolver/QueryPlan/Compiler 最小双表关系消费。
6. 忽略目录真实多表验收、项目日志和服务启动。

每个阶段按 TDD 实施并自动 Git 提交；不自动推送或合并。
