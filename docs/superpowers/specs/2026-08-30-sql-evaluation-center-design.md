# SQL 评测中心设计

日期：2026-08-30
状态：已确认，待编写实施计划

## 1. 背景与目标

项目当前已经能够在一次 `run_agent` 调用中同时产出 Legacy SQL 和本体影子 SQL，并返回本体命中状态、证据、时间决策与本体包版本。但是，现有能力只能逐条查看 SQL 差异，无法回答以下问题：

- 本体 SQL 在一组真实需求上的整体正确率是多少；
- 错误主要发生在对象选择、字段映射、关系、口径、账期还是 SQL 编译；
- 修改本体包或编译器之后，结果是提升还是退化；
- 哪些案例可以自动判定，哪些案例必须人工复核。

首期目标是在不执行 SQL、不连接业务数据库的前提下，建设一个可复现、可解释、可视化的 SQL 结构与语义评测闭环。用户上传仅包含“需求原文”和“真实 SQL”的 Excel 测试集，系统批量生成 Legacy SQL 与本体 SQL，进行确定性结构比较，并在独立的评测中心页面展示汇总指标和逐案例归因。

首期不以“查询结果完全相等”为结论，只评价可从 SQL 静态结构可靠推导的维度。

## 2. 已确认范围

### 2.1 首期包含

- 上传并校验现有两列 Excel 测试集；
- 按同一运行参数逐条调用现有 `run_agent`；
- 同时保存 Legacy SQL、本体 SQL、本体状态和本体证据；
- 使用 Python SQL AST 解析器进行结构标准化；
- 比较表、字段、JOIN、过滤条件、账期、聚合与查询形态；
- 生成单案例分项评分、严格通过结论和失败原因；
- 汇总本体生成率、严格通过率、平均得分及各维度正确率；
- 在前端增加独立的“评测中心”入口、进度页、汇总页和案例详情；
- 记录评测基准时间、本体包版本与哈希，支持前后结果对比的可追溯性；
- 支持删除评测任务及其敏感内容。

### 2.2 首期不包含

- 不连接 Hive、数据库或其他查询平台；
- 不执行真实 SQL，不比较结果集；
- 不把大模型裁判作为核心评分依据；
- 不自动修改本体、规划器或编译器；
- 不把测试集、真实需求或真实 SQL 写入 Git；
- 不建设复杂的多用户评测审批流；
- 不承诺静态结构评分等同于最终业务结果正确率。

## 3. 方案选择

### 3.1 采用方案：确定性 AST 结构评测

使用 SQLGlot 将真实 SQL、Legacy SQL 和本体 SQL 解析为抽象语法树，再提取统一的结构快照进行比较。首期 SQL 方言由评测任务显式指定，默认使用 Hive；解析器必须使用指定方言，不允许静默退回“猜测方言”。

选择该方案的原因：

- 相同输入会得到相同结果，便于做版本回归；
- 能消除大小写、空白、别名和字段顺序等无关文本差异；
- 能把错误定位到具体结构维度；
- 后续可以在不改变上层接口的情况下增加新方言解析器。

### 3.2 未采用方案

字符串或正则比较开发较快，但容易把等价 SQL 判错，也难以可靠识别子查询和 JOIN。大模型裁判能理解部分复杂业务语义，但会产生额外费用和不稳定结果。因此两者都不作为首期主评分器；大模型解释可以在后续作为人工复核助手单独设计。

## 4. 总体架构

```text
评测中心页面
  │ 上传 Excel + 设置基准时间、方言
  ▼
Evaluation API
  │ 创建任务、查询进度、读取结果、删除任务
  ▼
Evaluation Runner
  │ 逐案例调用现有 run_agent，限制并发并支持断点状态
  ├───────────────┐
  ▼               ▼
Legacy SQL      Ontology Shadow
                  │ SQL + 状态 + 证据 + 包版本
  └───────────────┘
          ▼
SQL Evaluation Core
  │ Parse → Normalize → Compare → Diagnose → Score
          ▼
Evaluation Store
  │ 任务、案例、结构快照、分项结果、失败原因
          ▼
评测中心汇总与案例详情
```

评测模块必须与聊天、取数执行模块隔离。它复用 `run_agent` 作为生成入口，但不经过聊天会话持久化，也不创建可执行取数任务，避免评测数据污染正常业务记录。

## 5. 后端组件边界

### 5.1 测试集导入器

输入为 `.xlsx` 文件，读取首个名为“测试案例”的工作表；如果不存在该名称，则在工作簿只有一个工作表时使用唯一工作表，否则拒绝导入。必填列为：

- `需求原文`
- `真实SQL`

导入器执行以下校验：

- 文件扩展名、文件大小和工作表数量合法；
- 两个必填表头存在且不重复；
- 每条非空数据行两个必填值均存在；
- 需求原文和 SQL 长度不超过服务端限制；
- 空白行被忽略；
- 至少存在一条完整案例；
- 每一行分配稳定的案例序号，不使用需求正文生成标识。

校验失败时返回行号和不包含敏感正文的错误信息，例如“第 4 行缺少真实 SQL”。首期不要求用户扩充模板列。

### 5.2 评测任务服务

创建任务时必须记录：

- 任务名称；
- SQL 方言，首期默认 `hive`；
- 评测基准系统时间；
- 测试案例总数；
- 创建人和创建时间；
- 当前状态与处理进度；
- 首次成功生成时解析到的本体包 ID、版本和哈希。

任务状态固定为：

- `pending`：等待执行；
- `running`：正在逐条生成和评分；
- `completed`：所有案例均已得到终态，包括案例级失败；
- `failed`：任务级错误导致无法继续；
- `cancelled`：预留给安全停止，不在首期页面提供复杂调度能力。

案例失败不得中断整个任务。每个案例独立记录生成、解析和评分状态，Runner 继续处理后续案例。Runner 首期采用单任务串行处理，避免批量请求同时消耗模型额度；架构上只暴露 `run_case` 和 `run_evaluation` 两层接口，不引入分布式队列。

### 5.3 Agent 适配器

评测服务通过窄接口调用现有 `run_agent`：

```python
evaluate_generation(requirement, system_time) -> GenerationSnapshot
```

`GenerationSnapshot` 只保留评测需要的信息：

- Legacy SQL 或生成失败原因；
- 本体 SQL；
- 本体状态；
- 本体摘要和证据；
- 时间决策；
- 本体包标识、版本和哈希；
- 单案例生成耗时。

评测层不得读取聊天数据库中的历史消息，也不携带对话上下文。每条需求均作为独立单轮需求执行，确保测试案例之间互不影响。

### 5.4 SQL 结构提取器

结构提取器接收 SQL 和显式方言，返回不可变的 `SqlStructure`。至少提取：

- 物理表名，统一为不带引号的小写限定名；
- SELECT 输出字段及表达式；
- `*` 是否存在；
- JOIN 类型、左右表及关联键；
- WHERE/HAVING 原子条件；
- 分区字段及其值或范围；
- 聚合函数及参数；
- GROUP BY 字段；
- DISTINCT；
- ORDER BY 与排序方向；
- LIMIT；
- CTE 和子查询是否存在；
- 解析警告和不支持结构。

字段别名和表别名先解析回源表达式再比较。无序集合在标准化后排序；有顺序语义的结构保持原顺序。字面量保留类型和值，不能只比较字段名称而忽略过滤值。

如果 SQLGlot 报告解析错误、返回非查询语句、包含多条语句或包含无法可靠理解的命令节点，该 SQL 标记为 `unparsed`，禁止用正则结果补齐后继续评分。

### 5.5 比较器与评分器

真实 SQL 的 `SqlStructure` 是静态评测参照。Legacy SQL 与本体 SQL 分别和真实 SQL 比较，互相之间的差异只用于展示，不作为正确性依据。

分项权重为：

| 维度 | 权重 | 主要比较内容 |
| --- | ---: | --- |
| 表 | 20 | 表集合的精确率、召回率和完全一致 |
| 字段 | 20 | 输出字段、表达式和 `*` 使用情况 |
| 过滤与业务口径 | 20 | WHERE/HAVING 字段、运算符和值 |
| JOIN | 15 | 关系两端、关联键和 JOIN 类型 |
| 分区与账期 | 15 | 分区字段、粒度、具体值或范围 |
| 查询形态 | 10 | 聚合、GROUP BY、DISTINCT、排序和 LIMIT |

每个维度返回 `matched`、`partial`、`mismatched`、`not_applicable` 或 `unscorable`，并附带缺失项、多余项和冲突项。数值得分只在参照 SQL 与候选 SQL 均成功解析且关键结构可评分时计算。

严格通过必须同时满足：

- 参照 SQL 与候选 SQL 均成功解析；
- 表、字段、过滤、JOIN、分区账期和查询形态全部为 `matched` 或双方均 `not_applicable`；
- 不存在不支持结构或解析警告；
- 候选 SQL 是单条只读查询。

总分用于观察改善幅度，严格通过率用于防止局部高分掩盖严重业务错误。无法评分的案例不计入平均结构得分的分母，但必须单独计入“待人工复核率”，不能按零分或满分处理。

### 5.6 失败归因器

失败归因优先使用本体运行状态和结构差异，不调用大模型。归因码至少包括：

- `ontology_no_match`：未命中查询概念；
- `ontology_ambiguous`：命中多个同等概念；
- `ontology_unsupported`：映射或规划能力不足；
- `ontology_unavailable`：本体包或运行链路不可用；
- `legacy_generation_failed`：Legacy SQL 生成失败；
- `reference_parse_failed`：真实 SQL 无法解析；
- `candidate_parse_failed`：候选 SQL 无法解析；
- `table_mismatch`：对象或物理表选择错误；
- `field_mismatch`：字段选择或表达式错误；
- `join_mismatch`：关系或关联键错误；
- `predicate_mismatch`：过滤条件或口径错误；
- `partition_mismatch`：分区字段或账期错误；
- `query_shape_mismatch`：聚合、分组、去重、排序或限制错误；
- `manual_review_required`：包含首期无法可靠判定的复杂结构。

一个案例可以有多个归因码。页面按优先级展示主因，同时保留完整原因列表。归因必须携带可验证的结构差异，不输出“语义可能不正确”一类不可操作描述。

## 6. 数据模型与持久化

新增两个应用数据库实体：

### 6.1 EvaluationRun

保存任务元数据、运行参数、进度、汇总指标、本体包版本和任务级错误。原始 Excel 文件不长期保存；导入成功后转换为案例记录，临时文件立即释放。

### 6.2 EvaluationCase

保存案例序号、需求原文、真实 SQL、Legacy SQL、本体 SQL、三份结构快照、生成状态、分项比较、得分、严格通过状态、失败归因和耗时。

需求原文和 SQL 属于敏感业务数据：

- 不写入应用日志和审计详情；
- API 列表默认不返回完整 SQL，只在案例详情接口返回；
- 删除评测任务时级联删除全部案例；
- 不进入 Git、内置样例和测试夹具；
- 后端异常只记录异常类型、任务 ID 和案例序号。

首期不额外保存 Excel 二进制，避免产生两份敏感数据副本。

## 7. API 设计

新增 `/evaluations` 路由组：

- `POST /evaluations/import`：上传 Excel、任务名称、方言和基准时间，校验后创建任务；
- `POST /evaluations/{id}/run`：启动尚未执行或允许重试的任务；
- `GET /evaluations`：分页查询当前用户的任务摘要；
- `GET /evaluations/{id}`：读取任务参数、进度和汇总指标；
- `GET /evaluations/{id}/cases`：分页读取案例摘要及筛选结果；
- `GET /evaluations/{id}/cases/{case_id}`：读取单案例完整三方 SQL、结构差异和本体证据；
- `DELETE /evaluations/{id}`：删除任务和全部案例。

首期运行进度使用前端轮询，不引入 WebSocket。重复点击运行接口必须幂等：运行中的任务返回当前状态，已完成任务不重复消耗模型额度；如需重新评测，用户创建新任务，以保留版本对比依据。

## 8. 前端评测中心

在主导航增加“评测中心”，路由为 `/evaluation`。页面分三层：

### 8.1 任务列表与新建任务

新建任务区域包含：

- 任务名称；
- Excel 文件选择；
- 格式提示和现有测试集模板下载入口；
- SQL 方言，默认 Hive；
- 评测基准时间，必填，默认显示当天但由用户确认；
- 文件解析后的案例数量；
- “开始评测”按钮和模型调用提醒。

列表展示状态、进度、案例数、严格通过率、本体生成率、平均得分、本体包版本和创建时间。

### 8.2 任务汇总

汇总页展示：

- Legacy 与本体的严格通过率；
- 本体 SQL 生成率、未命中率和待人工复核率；
- 两条路径的平均结构得分；
- 表、字段、JOIN、过滤、账期、查询形态六个维度的对比；
- 失败归因分布；
- 当前处理进度、失败数量和本体包版本。

指标必须同时展示分子和分母。例如“本体严格通过 3/7（42.9%）”，避免百分比掩盖样本量。

### 8.3 案例列表与详情

案例列表支持按以下条件筛选：

- Legacy 或本体严格通过；
- 本体状态；
- 主失败原因；
- 是否需要人工复核。

案例详情采用三栏或可切换面板展示真实 SQL、Legacy SQL 和本体 SQL，并展示：

- 每个维度的结论和分数；
- 缺失、多余及冲突结构；
- 本体命中的概念、属性、关系、规则和时间决策；
- 生成耗时和本体包版本；
- 无法自动判定时的明确原因。

页面不提供执行 SQL 按钮，防止评测与生产取数边界混淆。

## 9. 统计口径

- **本体生成率**：`ontology_status == generated` 的案例数 / 全部案例数；
- **本体未命中率**：`ontology_status == no_match` 的案例数 / 全部案例数；
- **解析成功率**：候选 SQL 成功形成可评分结构的案例数 / 该路径生成 SQL 的案例数；
- **严格通过率**：严格通过案例数 / 可评分案例数；
- **待人工复核率**：无法可靠自动评分的案例数 / 全部案例数；
- **平均结构得分**：可评分案例的结构总分算术平均值；
- **维度正确率**：该维度为 `matched` 的案例数 / 该维度可评分且适用的案例数。

汇总中必须分别给出 Legacy 和本体两条路径的数据。若分母为零，显示“暂无可评分案例”，不得显示 0%。

## 10. 基准时间与可复现性

每次任务使用统一的基准系统时间传入 `run_agent`。首轮测试可使用已约定的 `2026-08-24`，对应无显式时间需求时的默认推算示例 `p_day=20260822` 或 `p_mon=202607`；具体采用日分区还是月分区仍由本体中的对象时间策略决定。

任务执行期间如果检测到本体包版本或哈希发生变化，后续案例停止执行并把任务标记为失败，提示重新创建任务。禁止在同一个评测任务中混用多个本体版本，否则汇总指标不可复现。

## 11. 错误处理

- Excel 校验错误：拒绝创建任务，返回行号和结构化错误；
- 单案例 Agent 异常：记录案例失败并继续下一条；
- 真实 SQL 解析失败：标记参照不可评分和人工复核，不评价候选正确性；
- 候选 SQL 解析失败：记录候选解析失败，不进行结构分数计算；
- 本体未命中或不支持：保留本体状态，生成率统计为未生成，并给出失败归因；
- 本体版本变化：终止任务，防止混合版本；
- 服务重启：数据库中的已完成案例保留；再次启动运行时只处理仍为待执行的案例，不重复调用已完成案例；
- 页面轮询失败：保留任务 ID，恢复连接后继续查询，不自动重新提交任务。

## 12. 验证策略

本功能虽然不执行用户 SQL，但评测内核本身必须经过有针对性的验证：

### 12.1 后端单元验证

- Excel 表头、空行、缺失值、超长值和多工作表校验；
- SQL 大小写、空白、引号、别名变化仍能判定等价；
- 字段顺序变化在无顺序语义时不误判；
- 不同表、字段、JOIN 键、过滤值和账期能被准确归因；
- 聚合、GROUP BY、DISTINCT、ORDER BY 和 LIMIT 差异可识别；
- CTE、子查询及无法解析 SQL 正确进入人工复核；
- 严格通过、分母和平均分口径正确；
- 本体包版本变化会阻止任务继续；
- 敏感 SQL 不出现在日志与异常消息中。

测试 SQL 使用人工构造的虚拟表和字段，不复制用户测试集内容。

### 12.2 API 验证

- 创建、启动、轮询、分页、筛选、详情和删除流程；
- 重复启动不会重复执行；
- 当前用户不能读取或删除其他用户的评测；
- 删除任务会级联删除案例；
- 案例失败不会导致任务丢失进度。

### 12.3 前端验证

- 文件格式提示、错误行号和基准时间必填状态清晰；
- 运行中能看到案例进度；
- 汇总分子、分母与百分比一致；
- 案例筛选和三方 SQL 详情可用；
- 未生成、无法解析和待人工复核状态不会被展示成零分错误；
- 页面不暴露执行 SQL 的操作。

按照用户当前偏好，开发完成后只做与本功能直接相关的快速验证，然后优先启动前后端服务供用户体验；不在用户体验前进行大范围审查。

## 13. 首期完成标准

首期完成必须同时满足：

1. 用户可在评测中心上传现有两列 Excel 测试集；
2. 用户可设置统一基准时间并启动批量评测；
3. 7 条测试案例可以独立执行，单条失败不阻断整体；
4. 页面能看到 Legacy 与本体的生成率、严格通过率、平均分和六维指标；
5. 用户能打开任一案例查看三方 SQL、结构差异和失败归因；
6. 本体未命中可以归类到概念覆盖问题，而不是只显示笼统失败；
7. SQL 不被执行，敏感内容不进入 Git 或日志；
8. 同一评测任务固定本体包版本和基准时间；
9. 所有改动形成独立 Git 提交，不自动推送或合并。

## 14. 后续演进

首期积累稳定的静态评测基线后，再单独设计以下能力：

- 接入隔离测试数据库，比较结果集等价性；
- 增加业务指标级期望和允许误差；
- 对两次评测任务做版本回归对比；
- 使用人工审核结果校准评分权重；
- 为 MaxCompute、Presto、Spark 等平台增加方言适配；
- 根据失败归因生成本体补全建议，但不自动修改本体。

这些能力不在本次实施计划中预留额外抽象，待真实评测结果证明必要后再设计。
