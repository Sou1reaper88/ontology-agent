# 自然需求语义优先级设计

## 目标

让对话模型在需求模板变化、缺少“子需求”或“指标口径”等固定栏目时，仍能按自然语言含义确定本轮真正要交付的 SQL；避免把标题、背景说明或可选分析方向扩大成额外输出。

## 方案

保持 DeepSeek 同时负责需求理解、工具调度和 SQL 编写，不增加 Python 规则解析器，也不要求固定需求模板。仅收紧对话系统提示词中的语义优先级和阻断边界。

模型按含义而非栏目名称识别以下信息：

1. 当前明确要求完成的任务；
2. 用户要求的输出字段、结果表或交付形式；
3. 业务定义、筛选条件和统计范围；
4. 时间、地区等限定；
5. 用于解释目的的背景信息。

前四类共同决定 SQL，其中越明确、越接近当前动作的表述优先级越高。背景仅帮助理解，不得自行扩展查询周期、输出表或指标。用户最新纠正继续覆盖历史描述。

## 假设与阻断

- 缺少固定栏目不构成阻断。
- 没有指定输出字段时，模型可选择完成任务所需的最小字段集，并在 `assumptions` 中说明。
- 没有明确指标口径时，若能依据本体元数据和用户上下文作出可解释推断，模型继续生成 SQL，并把推断写入 `assumptions`。
- 未登记关系、用户明确给出的外部表字段、可选分析内容缺失，以及不影响核心输出的信息，只能作为假设或说明，不进入 `unresolved_items`。
- 只有直接冲突会实质改变结果，或缺少核心事实导致请求字段无法计算时，才写入 `unresolved_items` 并阻止正式交付。
- 不允许把静态校验通过等同于业务正确；现有 SQL 安全与结构校验保持不变。

## 改动范围

只修改 `agent/conversation_agent.py` 的系统提示词，并增加一个提示词契约测试。不会增加新模块、关键词分类器、固定模板解析、依赖或数据库变更。

## 验证

先用合成测试确认模型收到“不依赖栏目名、背景不得扩展、合理推断非阻断”的完整约束，再运行会话相关测试。随后通过正式会话接口复测最能暴露问题的需求：一条验证背景不会扩大周期，一条验证背景中的可选分析不会阻止明确输出。若两条改善，再决定是否消耗模型额度复测全部七条。

## 边界

提示词能改善模型遵循度，但不能数学上保证业务 SQL 正确。真实 SQL 仍需人工验收；发现稳定的业务定义后，应补入本体，而不是不断堆叠提示词规则。
