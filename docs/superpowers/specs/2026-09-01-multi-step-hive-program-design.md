# 智能取数多步骤 Hive 程序设计

日期：2026-09-01
状态：已确认，待编写实施计划

## 1. 背景与问题

当前 `run_agent()` 已经能够理解自然语言取数需求、检索本体元数据、推导账期并生成 SQL，但运行链路存在不一致：

- 生成提示词要求复杂需求使用 `DROP TABLE IF EXISTS` 和 `CREATE TABLE AS SELECT` 物化中间结果；
- 现有本体 `QueryPlan` 和 `GenericSqlCompiler` 只表达、编译单条查询；
- 确定性回退模板只返回单条 `SELECT`；
- SQL 评测器只接受单条只读查询；
- 用户提供的真实案例是由多组 `DROP/CREATE AS SELECT` 组成的 Hive 取数脚本，因此全部被标记为 `multiple_statements`；
- 本体管理数据此前运行在系统临时目录，服务重启后草稿和已发布版本不可恢复，导致本体路径无法参与评测。

本阶段将智能取数的核心输出从“单条查询”升级为“多步骤、可解释、可校验的取数程序”。大模型负责需求理解和步骤规划，本体负责约束业务语义，确定性编译器负责生成完整 Hive 脚本。评测中心随后按程序结构和表血缘评价真实脚本。

## 2. 已确认决策

1. 每个取数需求默认生成完整结果表脚本，而不是只返回 `SELECT`。
2. 系统只生成和校验脚本，不自动执行任何 SQL；执行仍属于独立操作和人工确认边界。
3. 结果表和中间表均由系统统一命名，不接受用户或大模型提供的物理目标表名。
4. 大模型负责生成结构化意图和多步骤计划，本体与规划器负责校验，编译器确定性生成 SQL。
5. 采用自适应两阶段模型调用：首次同时生成意图和计划；仅在结构化校验可修复时进行一次定向修复。
6. 首期只允许 `DROP TABLE IF EXISTS` 和 `CREATE TABLE AS SELECT`，不支持 `INSERT`、`ALTER`、`TRUNCATE` 或其他 DDL/DML。
7. 生成脚本不在末尾清理中间表，只在每张目标表创建前执行 `DROP IF EXISTS`。
8. 新链路开发完成后直接成为聊天页面默认输出；旧链路仅作为受控回退。
9. 首期实现 Hive 程序编译器，但规划契约和编译器接口不得依赖 Hive，后续可注册其他平台编译器。
10. 本体草稿、版本和活动版本指针迁移到项目目录外的持久化数据目录，不再使用系统临时目录。

## 3. 目标与非目标

### 3.1 目标

- 建立结构化 `IntentSpec`、`SqlProgramPlan`、`ProgramStep` 和 `CompiledProgram` 契约；
- 让 LLM 输出语义计划而不是任意物理 SQL；
- 使用当前本体包绑定概念、属性、关系、规则、物理映射和时间策略；
- 根据步骤依赖确定是否需要中间表，并构建无环表血缘；
- 统一生成安全、可重试的中间表和结果表名称；
- 将每一步查询确定性编译为 Hive CTAS 脚本；
- 对完整脚本执行多语句 AST、安全和语义校验；
- 保持 `run_agent()` 的现有 `sql` 返回字段兼容，同时暴露意图、计划、步骤和诊断；
- 让聊天页面默认展示完整建表脚本及规划证据；
- 让评测中心解析多语句脚本、规范化临时表名称并比较表血缘；
- 让本体数据在服务重启后继续存在；
- 使用外部真实测试集完成回归，但不把真实需求或 SQL 写入 Git。

### 3.2 非目标

- 不自动执行生成的 Hive 脚本；
- 不在首期支持任意结果表名称；
- 不支持 `INSERT INTO`、`INSERT OVERWRITE`、`ALTER`、`TRUNCATE`、`MERGE` 或存储过程；
- 不使用大模型直接生成并绕过校验的多语句脚本；
- 不建设通用工作流调度器、任务执行引擎或临时表自动清理服务；
- 不在本阶段实现 Hive 之外的真实程序编译器；
- 不使用真实 SQL 作为自动化测试夹具；
- 不把静态程序结构评分声明为查询结果完全等价。

## 4. 子任务拆分

本阶段包含两个边界独立、顺序执行的子任务：

### 4.1 本体持久化前置任务

将本体管理根目录配置为项目外的固定路径，确保草稿、不可变版本和活动版本指针在重启后保留。该任务只处理配置、路径校验和运行时加载，不修改规划器与编译器。

### 4.2 多步骤 SQL 程序主任务

实现意图、程序计划、校验、命名、编译、安全检查、聊天输出和程序级评测。主任务依赖一个可加载的已发布本体包，但不依赖本体管理目录的具体磁盘实现。

## 5. 方案选择

### 5.1 采用方案：LLM 结构化规划 + 本体校验 + 确定性编译

```text
自然语言需求
  → 确定性意图线索
  → LLM 输出 IntentSpec + SqlProgramPlan
  → 本体绑定与计划校验
  → 可选的一次定向修复
  → 系统目标表命名
  → 方言程序编译器
  → 脚本安全校验
  → 完整脚本与解释证据
```

该方案保留大模型对复杂需求的理解能力，同时把物理表、字段、关联键、分区、目标表名称和语句类型控制在确定性系统内。

### 5.2 未采用方案

- **大模型直接生成脚本**：开发快，但长脚本容易截断，表血缘和危险 DDL 难以可靠验证，无法成为可复现编译链路。
- **完全规则化规划**：稳定但对复杂自然语言覆盖不足，需要持续硬编码业务规则，不适合当前通过真实案例快速迭代的阶段。
- **固定两次 LLM 调用**：意图与计划容易产生跨调用偏差，简单需求也会固定增加耗时和额度消耗。自适应修复只在需要时执行第二次调用。

```text

          run_agent()

         │           ▼
         │    Targeted Plan Repair
         │           │
```

`run_agent()` 继续作为统一兼容入口。聊天、评测和未来 Python API 调用相同规划与编译服务，不复制另一套 SQL 生成逻辑。

## 7. 结构化契约

### 7.1 IntentSpec

`IntentSpec` 只描述用户想得到什么，不包含物理 SQL：

- `task_type`：首期固定为 `data_extraction`；
- `output_mode`：首期固定为 `materialized_table`；
- `business_concepts`：业务概念 URI 或稳定短名；
- `requested_properties`：期望输出的语义属性；
- `business_constraints`：结构化业务过滤意图；
- `time_intent`：用户时间、粒度、来源和是否需要默认推算；
- `result_shape`：聚合、分组、去重、排序和限制；
- `ambiguities`：需要用户确认的冲突或多义项。

确定性提取器先给出明确时间、输出模式和显式业务词等提示。LLM 在同一次调用中输出 `IntentSpec` 和程序草案，避免意图与计划脱节。

### 7.2 SqlProgramPlan

`SqlProgramPlan` 表示一个完整取数任务：

- `program_id`：服务端生成的非业务标识；
- `package_id`、`package_version`、`package_sha256`；
- `data_source_id` 和方言；
- 已验证的 `IntentSpec`；
- 有序 `ProgramStep` 集合；
- 唯一最终结果步骤；
- 计划诊断和修复次数。

计划必须引用同一个本体快照。运行过程中本体版本变化时禁止继续编译。

### 7.3 ProgramStep

每个步骤只负责一次查询变换：

- `step_id`：计划内稳定标识；
- `purpose`：面向用户的自然语言说明，不参与 SQL 拼接；
- `source_objects`：本体概念对应的源对象；
- `source_steps`：依赖的前置步骤；
- `query_plan`：复用现有单查询 `QueryPlan`，表达投影、过滤、关联、聚合和时间条件；
- `materialization_role`：`intermediate` 或 `result`。

大模型不能填写物理输出表名称，也不能在步骤中嵌入任意 SQL 字符串。

### 7.4 CompiledProgram

编译结果为不可变数据：

- 完整 SQL 脚本；
- 有序语句列表；
- 每个步骤的目标表；
- 中间表和结果表集合；
- 源表到中间表、结果表的血缘边；
- 使用的物理字段、关系、规则和分区；
- 编译诊断、安全检查结果和生成模式。

## 8. 规划与自适应修复

### 8.1 首次规划

Planner 接收用户需求、确定性意图线索和本体可用语义摘要。模型只输出受 Pydantic/JSON Schema 约束的意图与步骤草案。

模型负责：

- 判断简单需求是否只需一个结果步骤；
- 判断多来源、重复聚合、复杂排除或可复用逻辑是否需要中间步骤；
- 选择语义概念、属性、关系、规则和步骤依赖；
- 说明每一步的业务目的。

模型不负责：

- 选择未出现在本体中的物理表或字段；
- 构造物理 JOIN 键；
- 生成目标表名；
- 拼接最终 SQL；
- 决定是否执行脚本。

### 8.2 本体绑定与校验

Binder 和 Validator 必须检查：

- 所有概念、属性、关系和规则存在；
- 每个语义元素在目标数据源上存在唯一有效物理映射；
- JOIN 使用本体定义的关系映射；
- 投影和过滤属性属于步骤可访问的对象；
- 每张有时间策略的源表存在有界分区决策；
- 步骤依赖无循环、无悬空引用且最终结果唯一；
- 同一步骤不能同时读取自身输出；
- 计划不存在无法解释的任意物理标识符。

### 8.3 定向修复

首次计划只要存在可修复的结构错误，就把错误码、步骤标识和允许候选项交给模型修复一次。第二次调用不得重新解释整套物理元数据，也不得收到可直接执行的 SQL。

修复一次后仍不合法时：

- 业务解释存在冲突，返回澄清问题；
- 本体缺少元素，返回具体缺失项；
- 计划形态超出能力，返回 `unsupported_program_shape`；
- 禁止继续自由重试或退回不受控多语句生成。

## 9. 系统表名

所有物化表由 `ProgramTableNamer` 生成：

```text
中间表：temp_oa_<program_id>_01
中间表：temp_oa_<program_id>_02
结果表：temp_oa_<program_id>_result_table
```

约束如下：

- `program_id` 由服务端生成，不包含需求正文、用户信息、真实表名或业务概念；
- 聊天消息和评测案例必须持久化 `program_id`，同一任务恢复或重试时保持一致；
- 名称只包含安全标识符字符，并受统一长度限制；
- LLM、用户输入和本体描述都不能覆盖目标表名；
- 评测比较时按步骤角色和血缘规范化目标表名称，不要求与真实脚本使用相同临时表名。

## 10. 编译器设计

编译器协议扩展为：

```python
compile_query(query_plan) -> CompiledQuery
compile_program(program_plan) -> CompiledProgram
```

首期新增 `HiveProgramCompiler`。现有单查询编译能力继续负责每个步骤内部的 `SELECT`，程序编译器负责按拓扑顺序组合物化语句。

每个步骤固定编译为：

```sql
DROP TABLE IF EXISTS <system_target>;
CREATE TABLE <system_target> AS
<compiled_select>;
```

程序编译器必须：

- 按依赖拓扑排序步骤；
- 将前置步骤引用绑定到系统生成的中间表；
- 保证最终结果步骤最后生成；
- 保留各源对象的分区条件；
- 生成稳定格式，便于审计、展示和评测；
- 不在脚本末尾生成中间表清理语句；
- 不执行 SQL，也不持有数据库连接。

`CompilerRegistry` 首期注册 Hive 程序编译器。规划和本体层只依赖协议，未来添加其他平台时无需修改 `run_agent()` 的核心流程。

## 11. 安全校验

`ProgramSafetyValidator` 使用显式方言解析完整脚本，拒绝正则兜底。必须满足：

- 语句仅为 `DROP TABLE IF EXISTS` 和 `CREATE TABLE AS SELECT`；
- `DROP` 与 `CREATE` 目标属于本次编译结果中的系统表；
- 本体源表只允许出现在 `FROM` 或 `JOIN`；
- 每个目标表恰好先删除一次、再创建一次；
- 每个 CTAS 内部是成功解析的只读查询；
- 后续步骤只引用本体源表或已经创建的前置步骤；
- 不存在重复创建、循环依赖、悬空引用或末尾清理；
- 不存在 `INSERT`、`ALTER`、`TRUNCATE`、`MERGE`、函数创建或其他命令；
- 目标表名完全等于 `ProgramTableNamer` 的结果。

任何安全错误都使整个脚本不可返回。系统不得只返回校验通过的部分 SQL。

## 12. run_agent 集成与回退

新程序链路开发完成后成为聊天默认路径。`run_agent()` 保留原有 `sql` 字段并增加：

- `intent`；
- `program_plan`；
- `program_steps`；
- `program_id`；
- `generation_mode`；
- `diagnostics`；
- 本体包和时间决策证据。

生成模式固定为：

- `program`：首次计划通过并编译；
- `repaired_program`：定向修复一次后通过；
- `wrapped_legacy`：程序规划失败，但旧链路生成的单条查询通过本体与安全校验，被系统包装为单结果表 CTAS；
- `clarification_required`：存在不可安全猜测的业务歧义；
- `unsupported`：本体映射或程序形态不足；
- `unavailable`：没有可用本体快照或编译运行环境。

旧链路回退只能接受一条成功解析的只读查询。它不得直接返回单条 `SELECT`，也不得返回模型自由生成的多语句脚本。包装后的结果仍必须通过完整程序安全校验。

## 13. 本体持久化

本体管理目录必须通过 `ONTOLOGY__MANAGEMENT_ROOT` 指向项目目录外的固定路径。当前本地环境建议配置为：

```text
D:\Projects\ontology-agent-data\ontology-management
```

要求：

- 应用不再自动使用系统临时目录；
- 未配置持久化目录时，管理与本体运行就绪状态明确失败，不静默创建临时本体；
- 路径解析继续拒绝落在源码仓库内，避免真实本体进入 Git；
- 草稿、不可变版本、活动版本指针和导入会话继续使用原子写入；
- 服务启动时恢复活动版本并安装只读快照；
- `run_agent()` 每次锁定包 ID、版本和 SHA-256；
- 运行中包版本变化时终止该次任务，避免混合本体；
- 当前已清理的临时草稿无法恢复，需要从用户源文件重新导入并发布。

本体持久化与程序编译通过只读快照接口连接，不允许规划器直接读写管理目录。

## 14. 评测中心适配

评测器从单查询结构升级为程序结构：

```text
Hive 脚本
  → 多语句 AST
  → DROP/CREATE 配对
  → 每个 CTAS 查询结构
  → 目标表角色识别
  → 表血缘图
  → 中间表名称规范化
  → 程序比较与归因
```

比较器不得要求候选脚本和真实脚本使用相同临时表名称，也不得仅因中间表数量不同就判定失败。中间表数量作为诊断信息；核心比较最终语义、来源、过滤、关联、分区和血缘。

评分调整为七个维度：

| 维度 | 权重 | 主要内容 |
| --- | ---: | --- |
| 来源表 | 15 | 物理源表集合及覆盖 |
| 输出字段 | 15 | 最终输出字段和表达式 |
| 过滤与业务口径 | 20 | 各步骤 WHERE/HAVING 条件和值 |
| JOIN 与关联键 | 15 | 关系两端、键和 JOIN 类型 |
| 分区与账期 | 15 | 每张源表的分区字段、值和范围 |
| 建表步骤与血缘 | 10 | CTAS 物化、依赖边和最终结果路径 |
| 最终结果形态 | 10 | 聚合、分组、去重、排序和限制 |

真实脚本或候选脚本只要包含首期不支持的语句，就标记具体不支持结构并进入人工复核，不按零分伪装为业务错误。

## 15. 前端行为

### 15.1 聊天页面

- 默认 SQL 区展示完整 Hive 建表脚本；
- 推理区展示统一意图、规划步骤、中间表角色、本体证据和时间决策；
- 明确展示 `generation_mode`；
- 需要澄清时展示问题，不展示不完整 SQL；
- 不新增自动执行行为，现有执行入口仍需要用户单独操作和确认。

### 15.2 评测中心

- 支持多语句脚本解析状态；
- 汇总七个程序级维度；
- 案例详情展示真实脚本、旧链路脚本和新程序脚本；
- 展示规范化血缘、步骤差异和主失败原因；
- 不把 `multiple_statements` 作为建表脚本的统一失败原因。

本阶段不进行大规模 UI 重构，只补充理解和评测新返回契约所需的可见信息。

## 16. 错误处理与隐私

- LLM 结构化输出无效：定向修复一次；
- 本体元素缺失：返回缺失概念、属性、关系或映射的安全标识；
- 意图冲突：返回澄清问题；
- 时间策略不足：返回 `temporal_clarification_required`；
- 步骤形态不支持：返回 `unsupported_program_shape`；
- 程序安全校验失败：返回稳定安全错误码，不返回部分脚本；
- 本体包未发布或无法加载：返回 `ontology_unavailable`；
- 编译方言未注册：返回 `unsupported_dialect`。

日志只记录任务/消息 ID、程序 ID、步骤 ID、错误码、本体版本和耗时，不记录需求正文、真实 SQL、候选 SQL、业务口径值或模型完整响应。评测数据继续存储在应用数据库中，并可按任务级联删除；真实测试集文件不进入 Git。

## 17. 测试策略

### 17.1 结构契约与规划测试

- `IntentSpec` 和 `SqlProgramPlan` 的合法、非法和歧义输入；
- 简单需求形成唯一结果步骤；
- 多来源、复杂排除和重复聚合形成有序中间步骤；
- 循环、悬空依赖和多个结果步骤被拒绝；
- 定向修复只执行一次并限制修复范围；
- 本体缺失与业务歧义返回不同错误。

### 17.2 编译与安全测试

- 单步骤结果脚本包含一组 `DROP + CTAS`；
- 多步骤脚本按依赖拓扑编译；
- 所有目标表名由系统生成；
- 源表不会成为 DDL 目标；
- 每张有时间策略的源表具有有界分区；
- `INSERT/ALTER/TRUNCATE`、末尾清理和任意目标表被拒绝；
- 旧查询回退只能包装成单结果 CTAS；
- Hive 编译器通过注册表调用，核心计划不包含 Hive 语法。

### 17.3 run_agent 与 API 测试

- 现有调用参数继续有效；
- `sql` 字段返回完整脚本；
- 新结构字段与生成模式可序列化；
- 聊天历史和评测独立单轮调用均能传入稳定 `program_id`；
- 澄清、不可用和不支持状态不会误报成功；
- 无自动 SQL 执行调用。

### 17.4 本体持久化测试

- 未配置目录时明确失败；
- 配置目录位于源码仓库时被拒绝；
- 导入、发布、重启后草稿和活动版本仍存在；
- 活动快照可被 `run_agent()` 加载；
- 原子发布失败不破坏上一有效版本。

### 17.5 程序评测测试

- 多组 `DROP/CREATE` 能形成可评分程序；
- 临时表名称不同但血缘等价时不误判；
- 来源表、字段、过滤、JOIN、分区和血缘差异可独立归因；
- 中间表数量不同不会单独导致严格失败；
- 不支持语句进入人工复核；
- 七维权重、分子和分母正确。

自动化测试只使用虚构的中性表、字段和口径。开发完成后再由用户外部测试集运行真实评测，不复制其内容到测试文件、文档、日志或提交历史。

## 18. 验收标准

1. 聊天页面默认输出完整结果表脚本，不再返回裸 `SELECT`。
2. 简单需求至少生成一组结果表 `DROP + CTAS`；复杂需求按计划生成中间表和结果表。
3. 页面可以查看意图、程序步骤、系统表名、本体证据和时间决策。
4. 脚本只包含允许的两类语句，且不会操作本体源表。
5. 新计划失败时只走受控查询包装回退或返回澄清/缺失原因。
6. 本体草稿和已发布版本在服务重启后仍存在。
7. 用户的七条真实脚本全部能被程序评测器解析，不再统一出现 `multiple_statements`。
8. 每条真实案例得到七维评分或具体不可评分原因。
9. 系统不自动执行任何脚本，真实测试集和本体数据不进入 Git。
10. 实现按独立逻辑自动 Git 提交，不自动推送或合并。
11. 开发完成后只运行直接相关的精简验证，随后启动前后端服务供用户查看。
