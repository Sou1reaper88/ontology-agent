# Multi-step Hive Program Generation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the default single-query `run_agent` path with an ontology-grounded, multi-step Hive program generator that returns safe `DROP TABLE IF EXISTS` plus `CREATE TABLE AS SELECT` scripts, never executes them, and can be evaluated against complete reference programs.

**Architecture:** One structured LLM call produces `IntentSpec` and a SQL-free draft program; deterministic Python binds every step to ontology query plans, validates the dependency DAG, assigns system-controlled table names, and compiles Hive SQL. A single targeted repair call is allowed only for machine-actionable validation failures; ambiguous business semantics return a clarification. Existing single-query generation remains a controlled fallback and is wrapped into one result-table CTAS program.

**Tech Stack:** Python 3.13, Pydantic v2, SQLGlot Hive dialect, FastAPI, SQLAlchemy JSON fields, React/TypeScript, Vitest, pytest.

## Global Constraints

- Generate scripts only. Neither chat nor evaluation may execute the generated statements.
- The first release permits only paired `DROP TABLE IF EXISTS` and `CREATE TABLE ... AS SELECT ...` statements.
- Never append cleanup statements for result or intermediate tables.
- All DDL target names are generated by the system; user-supplied target names are ignored as identifiers.
- Source ontology tables are read-only and must never appear as DDL targets.
- The LLM may plan semantics and dependencies but may not emit executable SQL in `SqlProgramPlan`.
- Ontology binding, time-partition policy, dependency validation, table naming, and SQL rendering are deterministic Python responsibilities.
- At most one repair LLM call is allowed after the initial planning call. Business ambiguity must ask the user instead of guessing.
- `run_agent` adopts the new program path by default. The legacy path is allowed only as an observable fallback with an explicit reason.
- Preserve the existing response `sql` field for compatibility; it contains the complete generated program.
- Real user test-set content stays in `D:\Projects\ontology-agent-data` and must not be copied into Git, logs, fixtures, or journal entries.
- Add focused tests before implementation. After each user-visible slice, start the services for manual review before broad review work.
- Each logical task gets an automatic Git commit; never auto-push or auto-merge.

- `ontology_core/program_compiler.py`: deterministic table naming, Hive statement rendering, and AST-based safety validation.

- `evaluation/program_comparison.py`: seven-dimension whole-program comparison.
- `evaluation/generation.py`, `evaluation/runner.py`: evaluate through the same default `run_agent` program path.
- `frontend/src/features/chat/ProgramPlanPanel.tsx`: render complete script, steps, mode, diagnostics, and copy action.
