# 2026-09 项目建设记录

## 本体状态在服务重启后丢失

### 现象

本体管理页面曾经能够读取草稿，但服务重启后草稿和活动运行时不可恢复，导致取数链路重新表现为本体不可用。

### 根因

管理状态曾落在临时运行目录，进程生命周期结束后没有稳定的恢复边界；就绪接口还在每次请求时尝试恢复，使启动问题与请求副作用混在一起。

### 解决方式

- 强制通过外部固定目录保存草稿、不可变版本和活动版本指针。
- 拒绝源码仓库、保留目录、系统临时目录和链接路径。
- 在 FastAPI lifespan 中只执行一次活动版本恢复。
- `/ready` 只读取运行时健康状态，并返回脱敏的稳定原因。
- 通过依赖注入保证发布器与查询链路使用同一个只读运行时快照。

### 可复用经验

智能体的本体不是普通缓存，而是生成结果所依赖的可版本化业务资产。仅实现编辑页面和内存加载不等于具备本体工程能力；还需要明确持久化位置、不可变发布、活动指针、启动恢复、快照一致性和备份边界。

### 验证方式

运行持久化路径、发布器、健康检查和管理 API 的聚焦测试；发布一个测试版本后记录版本号与摘要，重启后端并确认两者不变。记录中不保存真实表名、字段、SQL、口径或测试集内容。

## 从单条 SQL 生成迁移到可验证的多步程序

### 现象

旧链路让模型直接输出一条查询，难以表达中间结果、复杂排除和可复用步骤，也无法证明模型没有把源表当成 DDL 目标。

### 难点

- 模型需要参与业务拆解，但不能获得任意表名和 SQL 拼接权。
- 多步依赖必须保持拓扑顺序，且不能引用尚未物化的结果。
- 生成期间若本体版本变化，已规划的语义与编译时映射可能不一致。
- 旧链路仍需兼容，但不能让不受控的多语句或 DML/DDL 借回退通道进入结果。

### 解决方式

- 大模型只输出受 Pydantic 约束的意图、语义引用和步骤依赖，计划内不接受 SQL 或物理目标表字段。
- Python 绑定器完成本体解析、时间决策和 DAG 校验；只对可机器修复的引用错误允许一次定向修复。
- 确定性 Hive 编译器统一生成系统表名，每步仅允许一组 `DROP TABLE IF EXISTS` 与 `CREATE TABLE AS SELECT`，不生成末尾清理语句。
- SQLGlot 对完整脚本执行 AST 白名单校验，同时拒绝源表与系统目标同名、悬空中间表和额外语句。
- 编译前再次比对本体包 ID、版本和 SHA-256；发生变化时立即中止。
- 旧链路仅在结构化规划不可用或明确不支持时启用，且只包装恢复为单条只读查询的输出。

### 验证方式

使用虚构中性概念验证程序合同、DAG 绑定、Hive 编译、调用次数上限、快照变更中止和回退包装安全。服务冒烟检查只生成一组结果表脚本，不连接数据库执行，不记录真实需求或参考 SQL。

## 让上下文压缩跟随模型能力而不是固定常量

### 难点

上下文压缩需要在调用模型前决定是否触发，但不同模型的上下文窗口与最大输出差异很大。把 32K/4K 固定值写死会让长上下文模型过早压缩；直接切换到模型最大值又可能覆盖已有部署中更保守的输出限制。

### 解决方式

- 建立独立、不可变的模型 Token 能力档案，并为未知模型保留安全默认值。
- 使用“新显式参数、旧显式参数、模型档案”的三级优先级，保证新增能力不会破坏现有 `.env`。
- 同时考虑输入上限、总上下文窗口、实际输出预留和静态提示预留，避免只看一个数字导致请求越界。
- 当前部署已设置旧输出限制，因此接入模型档案后仍保持原有输出上限；只有未配置时才采用模型默认能力。

### 可复用经验

模型的能力上限、应用的单次生成上限和上下文管理预算是三个相关但不同的概念。Agent 平台应集中解析它们，再把同一结果提供给模型客户端和记忆压缩器，避免两个模块各自猜测模型容量。

### 验证方式

使用不含业务数据的单元测试覆盖模型缺省值、显式覆盖、旧配置兼容、未知模型回退和输入预算封顶，并运行上下文、规划器、编排器及会话接口的聚焦回归测试。

## 大规模元数据发布触发安全扫描误报

### 现象

少量对象可以完成本体校验，但导入更多对象和字段后，草稿页面没有阻断级诊断，发布阶段仍失败。

### 根因

凭据安全扫描把每个数据源和物理映射节点都计入固定的递归配置扫描预算。字段数量增长会同步增加物理映射数量，即使这些映射没有嵌套配置或凭据，仍会耗尽 1024 节点或 4096 边的预算，形成规模相关的误报。

### 解决方式

- 继续逐个检查所有数据源和物理映射根节点上的凭据型谓词，保持直接凭据检测不变。
- 只把从根节点延伸出的配置子图计入递归节点和边预算，使预算约束对应真正可能失控的嵌套遍历。
- 保留超预算时失败关闭、重复编码凭据名识别、共享配置去重和显式配置根扫描等安全边界。
- 增加超过 1024 个物理映射的回归场景，防止业务目录规模再次被误当成恶意配置深度。

### 可复用经验

安全预算应限制攻击者可控制的递归扩张，而不是限制正常业务资产总量。资源预算如果和表字段数量线性耦合，会把业务增长转化为稳定的拒绝服务条件；设计时需要区分“可信目录根的总规模”和“非结构化配置图的遍历复杂度”。

### 验证方式

运行凭据扫描专项测试，并将当前草稿构建到临时目录，确认对象、属性和映射均可完整解析。验证过程不发布版本、不切换活动指针，也不记录真实表名、字段或业务口径。

## 2026-09-04：把重复账期配置收敛为自动约定

### 难点与方案

仅在导入阶段生成时间策略，无法覆盖已经发布的旧版本；直接改写旧 RDF 则会破坏版本不可变性。本次将 `_D → P_DAY / T−2`、`_M → P_MON / 上一个完整自然月` 集中为应用规则，在加载时派生有效语义目录，保留原始包文件及摘要。新包构建和草稿展示使用同一约定，避免管理页面与取数两条链路各自解释账期。

字段必须确实存在且启用；缺失或重复映射阻断发布/查询，不虚构字段或退回全表扫描。明确账期仍覆盖默认值，补齐紧凑日账期识别，日/月运算复用日历算法，避免跨年月份直接减一出现非法值。

### 本次证据与边界

59 项相关规则、候选校验及编译测试通过；前端构建通过。只读加载当前发布版本的 19 个对象，17 个日表和 2 个月表均识别成功，未修改版本摘要。系统日期 2026-08-24 得到日账期 20260822、月账期 202607。该结果说明分区覆盖和日期计算有效，不代表业务 SQL 全部正确；本轮没有调用外部模型或执行 SQL。
