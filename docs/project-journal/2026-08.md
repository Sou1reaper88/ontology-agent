# 2026 年 8 月工程日志

## 2026-08-21：Python 本体内核重构设计

### 背景

现有项目能够读取数据库表结构、字段注释、关系和逻辑定义，并通过 LangGraph 编排生成 HiveSQL。但业务概念与物理表绑定，本体能力主要表现为增强型元数据层，缺少正式 RDF/OWL 模型和可执行约束。

### 难点与痛点

- `DbOntologyClient` 同时承担元数据读取、本体检索、字段映射和 SQL 校验，职责边界过宽。
- 本体对象基本等同于物理表，未来接入其他数据库和编译器时容易重复建模。
- 直接引入 Java 本体服务会扩大当前 Python 团队的技术栈和部署复杂度。
- 真实电信表名、字段和口径不适合硬编码进生产代码或公开测试夹具。

### 方案取舍

评估了三种方向：

1. Python 原生 RDFLib + pySHACL。
2. 保持 MySQL 元数据为事实源，仅导出 TTL。
3. 以 GraphRAG 为核心重建语义检索。

选择第一种方向。原因是它能够建立正式 RDF/OWL 与 SHACL 边界，同时保留 Python、FastAPI 和 LangGraph 技术栈；相比 MySQL-first 方案，业务语义可以脱离物理表；相比 GraphRAG，正式本体更符合结构化查询和多编译器目标。

### 解决方式

- 设计独立 `OntologyService`，拆分 Repository、Validator、Resolver、MappingRegistry 和 QueryPlanValidator。
- 使用版本化本体包作为事实源，MySQL 只作为候选数据导入源。
- 同时提供 Python SDK 和 REST API，并共享 Pydantic 契约。
- 首期旁路接入，不改动现有 Agent 和 HiveSQL 链路。
- 测试使用匿名中性概念；生产代码不硬编码真实业务字段。

### 验证证据

- 设计文档提交：`1dd3541 docs: 设计 Python 本体内核首期重构`。
- 设计范围已经确认：首期只建立正式本体层，后续再改造数据库适配和编译器。
- 当前状态：设计完成，尚未进入实现，不将计划能力表述为已交付成果。

### 可复用经验

在数据分析系统向 Agent 系统演进时，应先把业务语义、物理数据映射和查询编译拆成独立边界。LLM 适合负责理解和规划，正式本体负责概念与约束，编译器负责生成目标平台查询，执行器负责访问数据源。

## 2026-08-21：纯 Python 本体包内核首个实现里程碑

### 已交付范围

- 使用 Pydantic 2 定义稳定错误契约和不可变 DTO；公开 DTO 不持有 RDFLib 对象。
- 使用 YAML 清单加载版本化本体包，按固定角色解析 `core`、`domain`、`mappings`、`rules` 和 `shapes`。
- 使用 RDFLib 解析 RDF/OWL Turtle，使用 pySHACL 执行 RDFS 推理和 SHACL 约束校验。
- 把 SHACL 报告图转换为排序后的字符串型违规 DTO，避免向上层泄漏 RDF 图内部类型。
- 仅在完整解析、校验、摘要和序列化成功后原子替换当前快照；失败重载保留上一有效快照。
- SHA-256 摘要覆盖清单原始字节、固定角色名和五个本体文件的原始字节。
- 本阶段保持旁路实现，没有修改现有 Agent、前端、HiveSQL 生成或执行链路。

### 实际难点与解决方式

1. **项目声明了 editable install，但缺少多顶层包发现配置。**
   - 现象：`pip install -e ".[dev]"` 被 setuptools 拒绝，错误为 flat-layout 中发现多个顶层包。
   - 根因：初始 `pyproject.toml` 没有构建后端和显式 package discovery，README 中的安装命令实际不可复现。
   - 解决：声明 `setuptools.build_meta`，显式允许生产包并排除 `tests*`。随后 editable install 成功，安装 RDFLib 7.6.0 和 pySHACL 0.40.1。
   - 放弃：没有用“只单独安装两个新依赖”绕过项目打包问题，因为那会继续保留不可复现的标准安装流程。

2. **Pydantic 的 `frozen=True` 不能冻结嵌套字典。**
   - 现象：`PackageManifest.files[role] = value` 可以绕过模型属性冻结。
   - 解决：把公开类型收窄为 `Mapping`，验证后复制为 `MappingProxyType`，并增加序列化器和原地修改回归测试。
   - 放弃：没有只修改类型注解而继续存储普通 `dict`，因为这不能提供运行时不变性。

3. **仅检查解析后路径仍不能满足严格清单安全契约。**
   - 现象：解析后仍在包根内的 `nested/../core.ttl` 和包根内绝对路径会被接受。
   - 解决：先拒绝原始绝对路径和任何 `..` 路径段，再执行 `resolve()` 与根目录包含检查；后一道检查继续防止符号链接解析后越界。
   - 验证：新增两个修复前失败、修复后通过的边界测试。

4. **SHACL 返回 RDF 报告图，不适合作为稳定接口直接向上暴露。**
   - 解决：提取 focus node、path、message、severity 和 source shape 为字符串 DTO，并按 focus/path/message 排序，使报告可序列化且顺序稳定。

5. **快照既要支持 RDF 图消费，又不能被调用方修改。**
   - 解决：内部快照保存 N-Triples 字符串，每次调用复制方法时重新解析为新 Graph；只有候选包完全成功后才在 `RLock` 内替换引用。

6. **Windows 与多智能体执行通道存在工程流程摩擦。**
   - Windows Bash 创建进程返回 `E_ACCESSDENIED`，任务说明提取改用 PowerShell，并只写入 worktree 的 Git 内部记录目录。
   - 多个实现/审查子智能体出现长时间运行但不产出报告；采用有界等待、持久化 RED/GREEN 报告、主控制器接管和独立复审，避免把不可观察的子任务当作完成。

7. **RDF blank node 标识不能直接作为稳定 API 字段。**
   - 现象：相同输入在三个独立 Python 进程中产生三个不同的匿名 `source_shape` 字符串。
   - 解决：对 pySHACL 报告图执行 RDFLib canonicalization，给 blank node 加显式 `_:` 前缀，并使用违规 DTO 的全部字段排序。
   - 验证：修复前稳定性测试失败；修复后两个全新图的报告一致，三个独立进程输出相同 canonical shape ID。
   - 最终复审进一步发现合法 shape 可包含多个 `sh:message`，`Graph.value()` 会在独立进程中任取一个；改为收集、规范化、排序并用固定分隔符合并全部消息，同时加入三子进程自动化回归测试。

8. **重复读取文件会破坏摘要对快照的证明能力。**
   - 现象：RDF 解析后、摘要前若文件发生变化，不同 Graph 可以得到同一摘要；摘要读取和序列化失败还会泄漏原生 I/O 异常。
   - 解决：清单和五个角色文件各读取一次为不可变 bytes，RDF 解析和 SHA-256 共享同一批内容；缺失、权限和序列化失败统一映射为项目异常，失败时保留旧快照。
   - 验证：四个修复前失败的回归用例在实现后全部通过。

## 2026-08-23：本体编辑、语义解析与 Resolver 证据记录

### 已交付范围

- 将通用词汇固定为 `urn:ontology-agent:core#`，以 `oa:Concept`、`oa:Property`、`oa:Relation`、`oa:BusinessRule`、`oa:DataSource`、`oa:PhysicalMapping` 区分领域元素与 OWL 元词汇。
- 将标记 RDF 元素解析为冻结的 Pydantic DTO，并在发布候选快照成功后原子替换语义目录；失败候选保留上一有效快照与目录。
- 交付快照绑定、只读的 Python `OntologyResolver`：URI / short name / 首选标签查询，以及 Unicode 规范化和确定性排序的概念搜索。
- 交付空白外部包初始化、校验与检查 CLI；新增通用资源不包含领域实例，真实包通过显式外部路径访问。

现有 Agent、HiveSQL 编译器、执行器、REST 和前端在本里程碑没有改动；Resolver 还没有接入现有 Agent 链路。

### 难点、根因与处理方式

1. **历史 seed 让测试看似“随机失败”。**
   - 根因：`test_retrieval_returns_relations_and_defs` 断言了已不存在的历史逻辑定义 seed，不是 UTF-8 编码损坏。
   - 处理：以 monkeypatch 提供最小内存表、关系、字段和逻辑定义，测试改为验证组装契约。该独立测试通过；当时全量结果为 `112 passed, 1 skipped`。

2. **OWL 元模型与领域元素不能混为一谈。**
   - 根因：若 SHACL 对所有 `owl:Class` 生效，`core.ttl` 的通用词汇也会被误当成业务概念；单有 `owl:Class` 又无法告诉 Resolver 哪些是领域元素。
   - 处理：领域概念同时使用 `owl:Class, oa:Concept`，属性和关系使用对应 `oa:` marker；SHACL 只 target 六个 marker。解析器只暴露带 marker 的 URI 主体。

3. **多语言显示名和检索必须跨运行稳定。**
   - 处理：首选标签按中文、无语言标签、其他语言标签分层，并在层内按文本稳定排序；Resolver 对文本使用 NFKC、trim、casefold，搜索按五档匹配等级、规范化 short name、URI 排序。Task 5 最终 review-hardening 节点的 resolver focused 为 `13 passed`，ontology-core 为 `95 passed`，全量为 `179 passed, 1 skipped`；这些是该阶段时间点的结果，不等同于后续总回归。

4. **发布不能让失败的候选污染在线读模型。**
   - 处理：锁外完成 SHACL、语义解析、序列化和候选 `OntologySnapshot` 构造，仅在成功后锁内替换；无效规则、映射或引用失败时保留旧 snapshot/catalog。Task 4 初始完成时 focused `34 passed`、全量 `143 passed, 1 skipped`；审查修复后 parser/repository focused 达到 `57 passed`，字面量副本回归通过。

5. **RDFLib 默认字面量规范化会改变 RDF 文件表达。**
   - 根因：默认 Turtle / N-Triples 重新解析可把 `"001"^^xsd:integer` 规范化为 `"1"`，破坏 lexical form。
   - 处理：包读取与快照图副本使用独立 Turtle sink，并以 `normalize=False` 构造 Literal，避免修改全局 `rdflib.NORMALIZE_LITERALS` 造成并发副作用。真实 package/repository 回归覆盖读取和公开副本两条边界。

6. **凭据规则不能只按普通 URL 处理。**
   - 根因：只按 `#` 和 `/` 取 local name 时，`urn:...:connection-string` 可绕过 denylist。
   - 处理：fragment、层级 path 与 URN 最后 `:` 段分别提取，再进行 percent decode、NFKC、casefold 和 `-` / `_` 归一化；仅对 DataSource 与 PhysicalMapping 拒绝 host、port、username、password、token、secret、connection string 等凭据谓词，避免误判普通领域属性。

7. **初始化外部目录的安全性与可用性存在真实取舍。**
   - 根因：先检查空目录再覆盖会有 TOCTOU；路径清理也可能在同名路径被替换后删除用户内容，Windows junction 还可能绕过普通目录检查。
   - 处理：在同级随机 staging 目录写入，使用独占创建、根 reparse-point/junction 检查、提交前后精确六文件字节校验与原子 rename；失败时不自动递归删除未知路径。代价是失败 staging 与已有空目标的备份需要人工确认后清理，这是 fail-closed 的有意选择。Task 6 审查修复后 focused `43 passed, 1 skipped`，最终复核时全量 `222 passed, 2 skipped`。

8. **CLI 的机器契约要区分 stdout 与 stderr。**
   - 处理：成功 JSON 写 stdout；ontology 错误 JSON 写 stderr，保持一条可解析 JSON 和稳定 `code`、`message`、`details`。检查输出只含包 ID、版本、摘要与六类计数，默认不含标识符、源路径或加载时间。Task 7 review-hardening 用真实模块进程确认 malformed package 返回 exit 1、stdout 为空且 stderr 为单个 JSON。

9. **离线 wheel 验证不能虚报为 `python -m build` 成功。**
   - 事实：当前项目虚拟环境的 `build` 前端不可作为 `python -m build --wheel` 使用。未联网安装依赖。
   - 处理与证据：使用已有 setuptools/wheel 的离线 `pip wheel --no-deps --no-build-isolation --wheel-dir dist .` 构建，并以标准库 `zipfile` 确认 wheel 包含 `ontology_core/resources/__init__.py`、`core.ttl` 和 `shapes.ttl`。这证明资源打包，但不把它表述为未执行的 build 前端命令。

## 2026-08-24：本体驱动 SQL 影子模式

### 问题与目标

本体包、语义目录和 Resolver 已经完成，但仍与 legacy Agent 并行存在，用户从聊天页面和生成 SQL 中看不到本体改造的价值。首个接入里程碑因此选择影子模式：保留现有 SQL，同时用本体快照生成独立 SQL，并在同一消息中展示差异和语义证据。

### 已交付范围

- 扩展只读 Resolver，使其按优先级提供数据源与启用的物理映射。
- 新增平台无关 `QueryPlan` 和确定性 `OntologyPlanner`；无匹配、歧义或缺失映射时拒绝猜测。
- 新增 `SqlCompiler` 协议、编译器注册表和首个 Generic SQL 编译器；自然语言规划与方言编译分离，为后续 Hive、PostgreSQL、MySQL 实现保留接口。
- 新增外部本体包运行时和 Shadow Service；本体 SQL 完全由本体映射与结构化规则生成，不读取或改写 legacy SQL。
- 在 `run_agent` 完成 legacy 输出后追加本体规划步骤；结果复用现有 trace JSON 持久化，不引入数据库迁移。
- 聊天页增加双栏 SQL、差异摘要和本体证据面板；本体侧仅允许复制，并明确标记为不会自动执行的影子预览。
- 本机脱敏演示包位于 Git 忽略目录，生产代码和提交历史不包含演示表、字段或业务规则。

### 难点与解决方式

1. **底层语义能力没有产品可见性。**
   - 处理：在现有聊天链路后增加独立影子步骤，复用 trace 作为 API 与持久化载体，前端对比展示旧 SQL、本体 SQL 和命中证据。
   - 价值：无需替换现有可执行 SQL即可验证本体是否真正影响查询结果。

2. **直接从自然语言拼 SQL 会重新引入模型幻觉和平台耦合。**
   - 处理：拆成 `OntologyPlanner -> QueryPlan -> SqlCompiler`。Planner 只能选择本体中已发布的概念、属性、规则和映射；编译器只消费结构化计划。

3. **影子链路不能拖垮已有 Agent。**
   - 处理：把 `generated/no_match/ambiguous/unsupported/unavailable` 建模为稳定结果；影子异常转为安全状态，legacy 成功状态、SQL 和 `QueryHistory` 不变。

4. **演示效果与真实效果必须区分。**
   - 处理：本机外部包只证明技术闭环；不以脱敏演示结果宣称业务准确率。真实提升将在用户测试集上按表命中率、字段命中率、规则覆盖率、可执行率和人工接受率评估。

5. **全仓静态检查存在大量历史债务。**

## 2026-08-24：表格元数据生成业务本体包

### 问题与目标

此前系统已具备本体包、查询计划和影子 SQL，但缺少真实业务内容入口。直接手写 TTL 无法规模化，复用旧版 MySQL 元数据接口又会把 Python 本体内核绑定到单一数据库。本阶段增加与数据平台无关的 TSV 导入链路，使业务表和字段可以进入本体包，同时保持真实元数据不进入 Git。

### 已交付范围

- 新增冻结的表格元数据 DTO、中文列名解析、类型规范化、结构化质量诊断和本地覆盖配置。
- 新增 RDF 本体包生成器：对象转换为概念，字段转换为属性，同时生成数据源、表映射和字段映射；不生成推测性业务规则。
- 使用同级随机暂存目录完整生成和校验候选包，成功后才切换目标；失败保留上一有效包。
- 新增 `import-tabular` CLI，支持外部 TSV、物理命名空间、平台类型、方言、本地覆盖、诊断报告和显式替换。
- 查询计划器在概念名未出现时，可通过多个字段标签反推唯一所属概念；无法匹配属性时失败关闭，不再默认选择对象全部字段。
- 影子证据仅返回表映射、本次选择字段映射和规则依赖映射，避免大表把全部字段映射展示到聊天页面。

### 难点与解决方式

1. **本体引擎与本体内容容易被混为一谈。**
   - 根因：技术链路完成不等于已有业务概念、字段和口径；没有真实元数据时，日常需求必然未命中。
   - 处理：把元数据适配、质量分析、覆盖修正、本体生成和运行时加载分层。通用代码进入 Git，真实附件、覆盖、报告和生成包统一放入 `.local/`。

2. **字段描述质量不稳定，但不能让导入器擅自修正业务含义。**
   - 处理：结构错误阻断发布，空描述只警告，疑似语义冲突作为待确认项；用户确认的修正放入本地覆盖文件，不修改原附件，也不硬编码到导入器。

3. **中文字符相似度会产生大量语义冲突误报。**
   - 根因：把短文本字符 Jaccard 阈值当作语义判断，会将“代码/编号”等相关表达错误标记为冲突。
   - 处理：以真实导入报告暴露噪声后，先增加同义表达回归测试，再将规则收紧为高精度提示。复杂语义冲突留给后续有来源、置信度和人工确认的候选规则流程。

4. **新需求不应被历史 SQL 模板限制。**
   - 处理：历史需求只作为规则发现和回归证据。Planner 通过属性标签组合推断唯一概念，再由物理映射编译 SQL；本地验收使用多个未保存成 SQL 模板的字段组合，均由同一本体现场生成。

5. **大对象会放大证据模型中的无关信息。**
   - 根因：初版影子证据直接返回查询计划中的全部可用属性映射，大表会产生大量无关映射。
   - 处理：证据集合改为“对象映射 + 选择字段映射 + 已确认规则依赖映射”，并增加未使用属性不得出现在证据中的回归测试。

6. **终端 PATH 漂移会制造假基线故障。**
   - 事实：一次基线命令解析到 Python 3.7 的 Anaconda，而项目要求 Python 3.11 以上，表现为测试收集长时间无输出和标准库 API 缺失。
   - 处理：用最小 `python --version`、模块导入和单测收集定位运行时差异，随后固定使用项目虚拟环境的绝对 Python 路径。未把环境问题误修成代码问题。
