# 本体驱动取数智能体：项目建设 Handoff（项目经历版）

> 文档用途：支持简历撰写、面试讲解、作品集说明和后续交接。
>
> 口径：基于仓库 `main` 分支截至 2026-10-09 的建设记录与提交整理；不包含真实客户需求、表名、字段名、账号、SQL 或密钥。

## 1. 项目一句话

面向企业数据取数场景，构建了一个**本体驱动的 Hive SQL 智能体**：它能在自然对话中理解取数需求，按需检索已发布的业务元数据和字段映射，调用大模型生成只读查询或临时结果表脚本，并通过静态校验、审计、会话反馈与评测中心形成可追溯的持续改进闭环。

## 2. 业务问题与项目目标

### 原始痛点

- 数据分析人员面对大量表、字段、业务口径和账期规则，手工写 SQL 成本高，且容易选错表、字段或分区。
- 传统 Text-to-SQL 容易直接依赖模型记忆或将元数据拼入提示词，缺少正式业务语义、版本边界和可审计性。
- 企业取数不只需要一条查询语句，还需要符合规范的可落表脚本、有限分区范围、外部数据表边界和权限控制。
- 真实 SQL 的“写法差异”不必然代表业务错误，因此不能仅靠字符串比较评价模型效果。

### 项目目标

1. 将业务概念、物理表、字段映射、关系和口径从生成逻辑中解耦，沉淀为可版本化本体资产。
2. 让大模型保留自然语言理解和 SQL 编写能力，但只能在受控元数据、工具和静态校验边界内工作。
3. 生成 SQL 而不执行 SQL，减少数据访问风险；为后续多数据库、多编译器和接口化调用保留演进空间。
4. 用真实需求和参考 SQL 建立评测、反馈和本体维护闭环，而不是只展示“模型能生成 SQL”。

## 3. 当前架构概览

```text
用户需求 / 多轮对话 / 单轮提示词
              │
              ▼
对话模型（意图理解、口径分析、SQL 编写、工具调度）
              │ OpenAI Function Calling
              ▼
只读能力工具
  ├─ 表检索                 search_tables
  ├─ 字段详情               read_fields
  ├─ 物理字段映射           get_field_mappings
  ├─ 业务上下文/关系/规则    get_business_context
  └─ SQL 静态校验           validate_sql
              │
              ▼
Python 确定性边界
  ├─ 已发布 RDF 本体包快照
  ├─ 默认账期与分区策略
  ├─ SQL AST 安全/交付校验
  ├─ 外部表与临时表命名边界
  └─ 审计、权限、会话与反馈留存
              │
              ▼
仅返回 SQL 脚本 / 说明 / 假设 / 未确认项
（不执行 SQL）
```

### 核心设计原则

- **模型负责语义理解与 SQL 创作**：不把复杂业务表达限制在自定义 DSL 中；模型可按需调用工具，而非被固定流程绑死。
- **本体负责事实与约束**：模型不能凭空拥有字段、映射、关系和规则；事实从活动本体快照读取。
- **Python 负责确定性边界**：负责默认时间、对象/字段授权、SQL 安全与交付形式校验，不重写模型的业务 SQL。
- **历史和当轮上下文分离**：当前用户任务优先，避免历史建议、背景说明或旧任务扩大本轮取数范围。
- **失败可见而非伪成功**：未确认口径、占位符或交付校验失败时保留草稿及诊断，但不作为可执行结果。

## 4. 主要建设阶段与本人贡献

### 阶段一：Python 本体内核与版本化语义资产

**解决的问题**：原系统的“本体”更接近数据库元数据层，业务概念与物理表耦合，无法形成可验证、可发布、可复用的语义资产。

**实现内容**：

- 使用 RDFLib、pySHACL、Pydantic 构建 Python 原生 RDF/OWL + SHACL 本体内核。
- 设计版本化本体包：YAML 清单与 `core/domain/mappings/rules/shapes` 五类文件。
- 建立 `Repository / Validator / Resolver / Mapping` 等边界，公开接口使用冻结 DTO，避免泄漏 RDFLib 内部对象。
- 实现包安全加载、内容 SHA-256 摘要、原子快照发布与失败回退：无效候选包不会污染线上有效快照。
- 处理 Windows 文件路径、危险清单路径、RDF 空白节点稳定性、字面量 lexical form、跨进程稳定 SHACL 报告等工程问题。

**可写进简历的价值**：把数据口径与元数据从代码常量升级为可校验、可版本化、可回滚的语义资产，为智能体的可信生成提供事实边界。

### 阶段二：本体管理与发布运行时

**解决的问题**：仅有本体文件无法支持运营人员维护；服务重启后若不能可靠恢复活动版本，智能体会丢失语义能力。

**实现内容**：

- 建立本体草稿、对象/字段/关系维护、批量导入、校验、不可变版本发布与回滚能力。
- 活动版本通过外部持久化目录保存，服务启动时恢复唯一活动快照；`/ready` 分别暴露数据库与本体健康状态。
- 草稿采用修订号并发控制，避免页面旧数据覆盖新修改。
- 业务维护改动先进入草稿，再发布为不可变版本；生成链路只读取活动快照。

**业务闭环示例**：真实评测中确认“字段值只要包含某关键词即可”的业务规则后，将规则写入相应日表和月表字段描述，而不是把需求特例硬编码到系统提示词或 SQL 模板中。

### 阶段三：从固定编排转向单模型工具调用智能体

**解决的问题**：早期多层模型/编译链路容易限制复杂 SQL，且会把自然问答、需求澄清与 SQL 生成机械化。

**实现内容**：

- 将会话入口改为一个模型统一负责需求理解、口径分析、SQL 编写和工具调度。
- 使用 OpenAI Function Calling 协议注册 5 个无模型、只读工具：表检索、字段读取、字段映射、业务上下文、SQL 校验。
- 移除嵌套 SQL 生成工具入口；模型可零次或多次调用工具，顺序由其根据需求自行决定。
- 支持自然问答、解释 SQL、提出本体改进建议与正式取数并存；只有需要 SQL 时才生成脚本。
- 将模型调用、工具调用摘要、诊断、耗时和前端处理过程写入可追溯记录，同时不保存逐字内部推理。

**关键取舍**：没有继续扩展 Python 自定义关系 DSL 来覆盖窗口函数、HAVING、复杂排除等表达，而是让 LLM 写 SQL，Python 做可验证边界。这是对“生成灵活性”与“安全可控性”的折中。

### 阶段四：SQL 交付安全、账期与上下文工程

**实现内容**：

- 默认交付临时结果表脚本；用户明确只需预览或查询时才返回只读 SQL。
- 对结果表脚本校验 `DROP TABLE IF EXISTS` / `CREATE TABLE AS SELECT` 配对、临时命名空间、最终结果表命名、禁止覆盖源表和禁止末尾清理。
- 对基础扫描要求有限分区范围；明确账期优先，日表默认系统日减 2，月表默认上一个自然月。
- 通过语义优先级约束处理复杂需求：当前任务、当前输出和明确限制优先于背景，避免背景中的多个周期或指标被模型擅自带入。
- 增加未确认项/草稿降级机制：缺少决定结果的关键事实时不允许占位符 SQL 伪装为正式结果。
- 修复多轮模型在工具调用耗尽后无法输出最终 JSON 的边界问题，并控制模型与工具调用上限。

### 阶段五：评测、反馈与本体持续改进

**实现内容**：

- 构建 SQL 评测中心，导入“需求原文 + 真实 SQL”测试集，逐条调用当前会话智能体生成 SQL，但不执行 SQL。
- 支持单查询及多步 CTAS 程序的 AST 结构比较，覆盖来源表、字段、过滤、关联、分区、查询形态等维度。
- 对无法可靠追溯临时表字段血缘的案例标为“人工复核”，不误记为零分或严格通过。
- 区分历史 Legacy 评测与当前对话智能体评测，避免前端呈现无意义的双路径指标。
- 增加 SQL 回答反馈：用户可标记正确/需修改，维护者可跨会话审查；删除会话会级联清理反馈，避免遗留脱离上下文的业务 SQL。

**重要认知**：真实 SQL 不是唯一真值。评测发现生成 SQL 与参考 SQL 写法不同后，需要业务人工确认差异是否等价；确认后的规则应沉淀进本体，而不是仅追求字符串一致。

## 7. 关键难点、解决思路与面试表达

### 难点 A：如何避免 LLM 把不确定口径伪装成可执行 SQL？

**做法**：将“模型生成 SQL”和“系统认可其可交付”拆开。模型可保留草稿；若存在阻塞性未确认项、占位符或 SQL 交付校验失败，则系统保留诊断但降级为不可执行草稿。

**面试表达**：我没有把“模型返回 SQL”视为成功，而是建立了可交付性状态机，避免用户把看似完整但口径缺失的脚本直接用于生产。

### 难点 B：为什么不让 Python 编译器直接生成全部 SQL？

**做法**：保留 Python 对元数据、时间、权限和 AST 安全的确定性约束；让模型处理复杂业务表达、窗口函数、聚合和自然语言歧义。

**面试表达**：强行把所有业务语义收进 DSL，会造成 DSL 无限膨胀且限制模型能力。我选择“LLM 写 SQL + 工具取证 + 确定性校验”的分层架构，让每层做自己擅长的事。

### 难点 C：如何防止上下文导致任务范围漂移？

**做法**：在提示词与上下文装配层定义语义优先级：当前明确任务、输出要求、时间和地区限制优先；背景只用于理解，不能自动扩展结果周期或指标。

**面试表达**：我把上下文工程当作产品规则，而不是单纯拼接历史消息；重点防的是“模型答得很完整，但答错了问题范围”。

### 难点 D：如何评估复杂 SQL 的业务正确性？

**做法**：使用 sqlglot 抽取结构维度；多步 CTAS 只比较可可靠追溯的最终语义；遇到不确定血缘直接提示人工复核。真实 SQL 差异由业务人员确认，确认后的规则回写本体草稿。

**面试表达**：评测不追求 SQL 字符串完全相同，而是区分结构可比、业务待确认与不可自动判断三类状态，避免错误指标误导模型优化方向。

- 将风控数据分析中的“指标口径、字段血缘、数据质量和可追溯”经验迁移到智能体系统：以 RDF 本体承载业务语义，以 SHACL 校验本体质量，以 SQL AST 校验生成结果安全性。
- 面向复杂企业数据取数需求，设计从自然语言需求、元数据检索、SQL 生成、静态评测到人工反馈回写的治理闭环。

## 9. 60 秒面试讲解稿

我做的是一个本体驱动的企业取数智能体。它解决的不是简单的“自然语言转 SQL”，而是企业里真实存在的表很多、字段含义不一致、口径复杂、账期严格且 SQL 不能随便执行的问题。

架构上，我把系统拆成三层：底层用 RDF/OWL 和 SHACL 把业务概念、字段映射、关系和规则做成可发布的本体包；中间层由同一个大模型通过 Function Calling 按需检索表和字段，再自己编写 Hive SQL；上层 Python 不替模型改业务 SQL，只负责活动本体快照、时间分区、临时建表规范和 SQL AST 安全校验。这样既保留了大模型处理复杂业务表达的能力，也防止它绕过元数据或生成不可交付脚本。

后面我还做了评测和反馈闭环：真实需求和真实 SQL 可以导入评测中心，多步 CTAS 脚本按结构维度比较；如果字段血缘不能可靠推断，就标人工复核而不是误判零分。人工确认后的业务差异会回写本体草稿，经过版本发布后再影响后续生成。这一过程让我从数据分析的口径治理经验，真正迁移到了 Agent 的上下文工程、工具调用、评测和持续优化中。

## 10. 当前状态与后续可讲方向

### 已具备

- 版本化本体包、草稿维护、发布、恢复与健康检查。
- 对话式 SQL 智能体、工具调用、静态校验、临时表交付规则。
- 会话、权限、审计、反馈、本体维护与评测中心。
- 多步 CTAS 的保守结构比较和人工复核机制。

### 仍需持续建设（面试时可主动说明）

- 真实业务测试集规模仍有限，不能声称完整的生产准确率。
- 多步脚本的字段血缘分析采用保守策略，复杂表达式、分支和非直通字段会要求人工复核。
- 本体草稿规则需发布为新活动版本后才会影响线上生成；草稿与活动版本刻意隔离。
- 当前主要面向 Hive；下一阶段可扩展数据源接口和方言编译适配器，服务多数据库平台。
- 业务正确性最终仍需领域专家验收，静态校验和评测只能降低风险、缩短定位时间。

## 11. 使用提醒：哪些话不要写

- 不要写“自动执行 SQL”或“直接访问生产数据”：项目当前定位为生成与校验，不执行取数。
- 不要写“准确率 XX%”：目前没有足够规模、经业务人工最终确认的统计基线。
- 不要将真实客户表名、字段、手机号、业务口径或 SQL 放入公开简历、GitHub README 或面试材料。
- 不要把“已存在兼容模块”描述为当前默认链路；当前会话主链路是单模型工具调用，不是旧的固定编译器流程。

## 12. 交接清单

1. 本地启动使用项目根目录 `start.bat`，不要从 `.worktrees` 目录启动。
2. 后端健康检查：`http://127.0.0.1:8001/ready` 同时应显示数据库与本体 `ok`。
3. 本体修改先进入草稿；只有发布为活动版本后才影响会话生成。
4. 评测调用模型会消耗额度，但只生成和比较 SQL，不执行 SQL。
5. 提交代码前保留已有未跟踪/构建缓存文件，避免把 `.env`、真实测试集、本体管理外部目录或服务日志推送到远端。
