# ADR-0001：使用 Python RDFLib 与 pySHACL 建立正式本体内核

- 状态：已接受
- 日期：2026-08-21

## 背景

项目当前通过 MySQL 表结构、字段注释、关系表和逻辑定义提供轻量本体能力。未来需要支持多种数据库和查询编译器，因此业务概念不能继续等同于某个数据库中的物理表。

团队希望继续使用 Python 开发，并保留现有 FastAPI 与 LangGraph 架构。

## 决策

使用 RDFLib 作为 RDF/OWL 加载与查询基础，使用 pySHACL 执行本体包约束验证。版本化 TTL 本体包成为语义事实源，并通过 Python SDK 与 REST API 对外提供能力。

首期以旁路方式接入，不替换现有 Agent、SQL 生成和执行链路。

## 备选方案

### MySQL 元数据继续作为事实源

优点是改动小，现有管理界面可以直接复用。缺点是业务概念仍然容易绑定数据库表结构，难以支撑后续多平台编译器。

### Apache Jena/Fuseki

具备成熟的 RDF、OWL、SPARQL 和推理能力。缺点是需要引入 Java 服务和额外部署单元，不符合首期纯 Python 的约束。未来本体规模和推理需求增长后可以重新评估。

### GraphRAG

适合从非结构化文档构建图并增强问答，但不能替代正式本体、SHACL 约束和结构化查询映射，因此不作为本项目本体核心。

## 后果

正面影响：

- 业务概念与物理数据库解耦。
- 可以用标准 RDF/OWL 和 SHACL 表达、验证语义。
- 与当前 Python 技术栈兼容。
- 为统一 QueryPlan 和多编译器提供稳定输入。

需要承担：

- 团队需要建立 RDF、OWL、SHACL 和 URI 设计能力。
- RDFLib 不等同于高性能图数据库，未来可能需要替换 Repository 实现。
- MySQL 元数据到正式本体需要经过确定性导入和人工审查。
